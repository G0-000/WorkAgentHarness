# 02 — EvoFlow → AgentFlow 第一版 → WorkAgentHarness 全量功能矩阵

> 本文件是 WorkAgentHarness M0–M8 唯一持续维护的逐功能清单。当前模板提供字段和规则；空表不代表盘点已完成。必须以固定 EvoFlow 快照为准逐项盘点，并把 AgentFlow 第一版作为比较材料、WorkAgentHarness 作为新实现目标。

## 文档职责

- [01-功能域初始对照](01-功能域初始对照.md) 是域级导航和盘点起点，不承担逐功能记录，也不作为完成度统计来源。
- 本文件按**可独立验收的行为/能力**拆行。功能描述、路径映射、差异和当前阶段状态只在这里维护。
- [09-完整功能对照与最终验收](09-完整功能对照与最终验收.md) 是收口规则和验收结果视图；引用本文件的功能 ID，只补验收结论、证据和关闭日期，不复制功能描述。
- 章节文档可记录本章执行过程，但逐功能状态应回链本文件的 ID，避免多份状态表漂移。

## 纳入规则

1. 从 EvoFlow 路由、CLI 注册、应用装配、前端路由、配置 schema、数据库迁移、测试、文档和运行入口交叉盘点一方能力。
2. 一个目录可能包含多个行为；多个目录也可能共同组成一个用户行为。按真实调用链和责任边界拆分，不按目录机械计数。
3. 仅在同一行为、同一责任边界且可以用同一组验收条件验证时合并。不同入口、权限或生命周期会改变行为时应拆行。
4. 分别填写 AgentFlow 第一版路径/行为和 WorkAgentHarness 当前路径/状态；WorkAgentHarness 尚无实现时写“缺失”，尚未核验时写“待核验”，不能留空或用目录存在作为实现证据。
5. 排除项仍保留 ID，填写具体理由、证据和兼容替代方案；“暂不做”“复杂”不是排除理由。
6. 每条能力都有唯一稳定 ID（建议 `WAH-<域>-<三位序号>`，如 `WAH-M7-001`）；ID 一经引用不因重排而复用。

## 状态和验收类型

阶段状态建议使用：`待盘点`、`已盘点`、`待实现`、`实现中`、`待验收`、`已验收`、`有条件排除`。只有证据满足章节完成门槛后才可标记“已验收”。

验收类型至少说明适用层级：`unit`、`integration`、`e2e`、`manual`；注明 mock/真实依赖、入口、命令或操作步骤、结果位置、日期和 commit。真实外部联调未完成时，明确记录替代测试与未验证限制。

## 全量功能矩阵

M0 完成前先按下表扩展记录。每个单元格应写可复核内容或明确状态，不得以“见代码”“同上”代替。

| 功能 ID | EvoFlow 快照路径/入口/测试 | 可观察行为与边界 | 依赖、配置及前置条件 | AgentFlow 第一版路径/符号与实际行为 | WorkAgentHarness 路径/符号与状态 | 所属章节/学习级别 | 阶段状态 | 验收类型与证据 | 差异理由/排除依据 |
|---|---|---|---|---|---|---|---|---|---|
| WAH-<域>-001 | 待 M0 盘点：文件/符号；真实 caller/route/CLI/UI；相关测试 | 待 M0 描述输入、输出、错误、权限及生命周期 | 待核验配置、存储、外部依赖和先决能力 | 待 M0 复核第一版真实路径与行为 | 当前仓库无实现；设计确认前写“待设计”，无实现时写“缺失” | Mx / Lx | 待盘点 | 待执行；写明 unit/integration/e2e/manual、mock 情况、操作/命令、结果、日期和 commit | 无差异则写“待比较”；排除需写具体证据和替代方案 |

## M0 盘点出口

- 01 中每个域和跨章条目都已映射到一个或多个稳定功能 ID；新增发现的域也进入本矩阵。
- 对照 EvoFlow 当前快照核验了所有应用入口、注册点、装配点、配置、迁移、测试和 UI 路由；孤立代码需单独标注“无真实入口/未集成”。
- 所有记录至少有 EvoFlow 证据、行为描述、章节归属、AgentFlow 第一版参考状态和 WorkAgentHarness 设计/实现状态；未完成核验明确写“待核验”，不伪装成完整盘点。
- M0 盘点只有在覆盖审查通过后才可关闭。后续章节继续更新本矩阵的实现、验收和差异字段；09 只引用 ID 并记录收口结论。
