# 规划与快照更新规则

这份规则回答一个问题：**EvoFlow 一直在变，课程结构凭什么保持正确？**

结论是：篇数、章数、功能 ID 数都不是固定结构，只是某一次快照下的结果。每次重新规划都从最新源码重盘，而不是在旧表上修补。

## 1. 何时触发重新规划

满足任一条件就重盘，不要等"攒够了再改"：

| 触发 | 说明 |
|---|---|
| EvoFlow HEAD 变了 | 仓库 HEAD 前进（如 2026-11-10 已到 `f22af53`/1.3.22）**不自动改学习快照**：学习目标固定为目标 sha，只有决定换快照时才重盘；换快照需保留旧快照证据 |
| 发现新的用户入口 | 新路由、新渠道、新 CLI 参数、新页面 |
| 发现原判断是错的 | 例如"原版没有某能力"被推翻 |
| 学习者进度推进到新篇 | 进入下一篇前重盘该篇范围 |
| 章节验收跑不通 | 说明文档与代码已脱节 |

## 2. 五步流程

### 第 1 步：读三仓状态（不改任何东西）

```bash
git -C /Users/main/EvoFlow rev-parse HEAD && git -C /Users/main/EvoFlow status --porcelain | wc -l
git -C /Users/main/WorkAgentHarness rev-parse HEAD && git -C /Users/main/WorkAgentHarness status --porcelain | wc -l
git -C /Users/main/agent-book rev-parse HEAD && git -C /Users/main/agent-book status --porcelain | wc -l
```

三个数字都要记：**HEAD + 未提交条数**。未提交条数是保护线，后面所有同步都按它做增量，不许整目录覆盖。

### 第 2 步：差异盘点（只看"变了什么"）

```bash
git -C /Users/main/EvoFlow diff --stat <旧快照> <新快照>
git -C /Users/main/EvoFlow diff --name-status <旧快照> <新快照>
ls -1 /Users/main/EvoFlow/backend/packages/harness/evoflow/
ls -1 /Users/main/EvoFlow/backend/app/gateway/routers/ | wc -l
ls -1 /Users/main/EvoFlow/backend/app/channels/
```

产出一张差异表，每行归入五类之一：

| 类别 | 含义 | 处理 |
|---|---|---|
| 新增 | 新目录/新类/新入口 | 补功能 ID + 补章或并入现有章 |
| 改名 | 同职责不同名 | 改文档引用，**不新增 ID** |
| 迁移 | 文件换位置 | 改阅读路径 |
| 删除 | 能力下线 | 标废弃，不直接从课程里抹掉 |
| 行为变化 | 同符号语义变了 | 重写该节 + 重跑验收 |

### 第 3 步：按行为重盘能力（这一步最容易翻车）

**铁律：判断一个能力是否存在，看行为，不看类名。**

```bash
# 1. 先看目录有哪些文件
ls -1 <目标目录>
# 2. 再看每个文件里有什么类/函数
grep -nE "^class |^def " <目录>/*.py
# 3. 读文件头 docstring
head -30 <文件>
# 4. 最后按功能搜全仓库（必须包含 backend/app/）
grep -rl "入站消息" /Users/main/EvoFlow/backend | head
```

**为什么强调第 4 步**：本项目已经因为"只搜核心包"翻过四次车——

| 翻车 | 错在哪 | 真相 |
|---|---|---|
| `ChatModelConfig` | 按名字搜不到就判"没有" | 原版用别的名字实现了同一职责 |
| `knowledge/owned/kg.py` | 只搜 `evoflow/` | 能力在应用层 |
| `scheduler/` | 只看目录名 | 调度在别的模块里 |
| `channels/` | 只搜核心包，没搜 `backend/app/` | 渠道层一直存在，第 46 章整章写错前提 |

所以顺序固定为：**目录清单 → 逐文件符号 → docstring → 按功能搜全仓库 → 才下结论**。名字不同**不能**作为"不存在"的证据。

### 第 4 步：重新决定章节

章节跟着**概念和代码依赖**走，不跟着旧编号走：

| 情况 | 动作 |
|---|---|
| 一个能力跨 3 个以上子系统 | 拆章，或明确标"专题 + 前置知识" |
| 两个章节讲同一能力 | 合并，或写清递进关系（谁是谁的前提） |
| 新能力无归属 | 新开一章，不硬塞进已有章 |
| 某章只剩设计没有代码 | 标"设计章"，验收降为文档级 |
| 篇章数量变化 | 直接改，同步改篇号口径与所有交叉引用 |

篇号只有一套：**按目录序号**，`一-导学` 是第 1 篇，依次到第 13 篇。课程目录、教程册 README、各篇 README 必须用同一套。

### 第 5 步：更新状态与证据

状态只写进[功能清单](功能清单.md)，其他页面引用它，不各自维护。

| 状态 | 含义 |
|---|---|
| 待盘点 | 还没按行为核实过 |
| 已盘点 | 核实了 EvoFlow 侧行为，有路径与符号 |
| 已理解 | 能讲清调用链与状态 |
| 最小闭环 | 单点跑通，无真实入口 |
| 功能补齐中 | 接了入口，边界未验 |
| 边界待验 | 主路径通过，失败/恢复/权限未验 |
| 已验收 | 四类核验都有证据 |

写"已验收"必须同时有：EvoFlow 文件:行、本项目文件:行、真实入口命令、预期、实测输出、至少一条失败用例。

## 3. 什么不算完成

以下四条都不能替代验收，任何一条单独成立都不足以标"已验收"：

1. 教程写完了 / 章节齐全；
2. 代码文件存在；
3. 之前某一轮跑通过（换了快照就作废）；
4. 目录覆盖率高。

## 4. 同步规则（写文档之后）

- 先 `filecmp` 逐文件比对两边，再 `shutil.copy2`，**禁止整目录覆盖、禁止 `rsync --delete`**；
- 任何一边有未提交改动，先辨认内容，再在其基础上增量改；
- agent-book 的 commit/push 由用户执行，本流程只做文件与构建验证。

1. 第 1–13 章的旧运行结果仍是有效历史记录，但快照一致性项已过期；后续篇学习从新快照开始，不倒改旧实测日期和输出。
2. 开第 4 篇前，先在前三篇涉及的新旧交界处做一次定向复核：模型选择、工具/schema、事件、thread/run 恢复；记录是否影响 WorkAgentHarness 既有实现。
3. 每个上表新行为落章后，补 `EvoFlow 路径/符号/调用者/测试` 和本项目差异；只看到新增文件不算盘点完成。
