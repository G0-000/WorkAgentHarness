## 场景

你让 Agent 改一个方法："把 `RunService.execute` 的取消逻辑改掉。"

Agent 必须先回答三个问题：

1. **这个方法在哪**？（`persistence/run_repository.py` 还是 `service/run_service.py`？）
2. **谁调用它**？（改了签名会崩哪几个文件？）
3. **它依赖哪些类型**？（改返回值，哪些地方要跟着改？）

靠 grep 能回答第一个，回答不了第二、三个——因为调用可能是别名导入（`from x import y as z`），类型可能是泛型（`List[RunResult]`）。

这就是代码索引要做的事：**把"符号、导入、引用、类型关系、文件依赖"抽成表，让 Agent 能查结构而不是查字符串**。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 只靠 grep 找符号 | 别名导入、同名符号、字符串里出现的名字都会误判 |
| 索引库不分工作区 | 两个项目的 `utils.py` 撞在一起 |
| 不做导入绑定 | `from a import f as g` 后，`g()` 的引用查不到 `a.f` |
| 不做类型关系 | 改返回类型时，下游调用点全漏 |
| 每次全量重建 | 大仓库一次索引几分钟，改一行也要等 |
| 无 watcher | 索引与磁盘不同步，查到的是旧代码 |

| ⑫ 结果格式化 | `format_results.py:8` `format_search_index_body(...)`；`:42` `_symbol_rank`（定义优先于引用） | 给模型看的排序结果 |

**四种解析器的优先级（这是最容易忽略的一点）**：

```
LSP（最精确，需启动语言服务器）
  ↓ 不可用
tree-sitter（多语言，语法级）
  ↓ 不可用
AST（仅 Python）/ javalang（仅 Java）
  ↓ 不可用
正则（兜底，会误判）
```

逐层追读要点：

1. **入口**：谁触发建索引（打开工作区 / 首次搜索）。
2. **调用者**：`resolve_index_root` 被哪些模块调用。
3. **核心决策**：`_workspace_hash` 用什么做 key（绝对路径？git 根？）。
4. **状态**：`file_deps` 与 `internal_refs` **各有双向索引**（from/to），说明两个方向都要快查。
5. **返回**：`format_search_index_body` 的排序——**定义类符号排在引用前**（`_symbol_rank`）。
6. **证据**：`_load_sqlite_vec_extension` 说明代码检索也走向量，不只是符号表。

## 调用流程

```text
工作区打开
  ▼
① 定位索引库   resolve_index_root → _workspace_hash → index_db_path
  ▼
② 建表连接     _configure_sqlite_connection → _load_sqlite_vec_extension
  ▼
③ 逐文件解析   language_for_path → parse_tree(tree-sitter)
  │              └ 失败 → _ast_python_symbols / _javalang_symbols → 正则兜底
  ▼
④ 抽三类关系   import_aliases_for_file（别名）
  │             extract_internal_refs（引用）
  │             enrich_type_relations（类型）
  ▼
⑤ 落表        symbols / file_deps / internal_refs
  ▼
⑥ 增量更新    start_index_watch → CodeIndexWatcherRegistry → 文件变更重解析
  ▼
⑦ 查询返回    format_search_index_body（定义优先）→ 给模型
```

## WorkAgentHarness 现状与设计

**现状**：没有代码索引。第三篇的 `workspace_file.py` 只能按路径读文件，Agent 找符号只能靠模型自己读。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 索引库位置 | `<workspace>/.wah/index.db`，路径 hash 记在 `meta` 表 | 不按 hash 分目录，直接放工作区下 |
| 解析器 | **只用 Python `ast`**（`_ast_python_symbols` 同思路） | 不做 LSP / tree-sitter / Java |
| 符号表 | `symbols(name, kind, path, line)`，`kind` ∈ `class/function/method` | 对齐原版字段 |
| 导入绑定 | 抽 `ImportFrom` 的别名映射，落 `import_aliases(file, alias, target)` | 只做 Python |
| 引用 | `refs(name, path, line, kind)`，`kind` ∈ `call/import/definition` | 不做跨语言 |
| 文件依赖 | `file_deps(from_path, to_path)` | 双向索引 |
| 类型关系 | **不做** | `enrich_type_relations` 成本高，收益在大型仓库 |
| 增量 | 只在启动时全量扫一次，不做 watcher | 不做文件监听 |
| 排序 | 定义优先于引用 | 对齐 `_symbol_rank` |
| 向量 | 不做 | 不做 sqlite-vec |

**为什么砍掉 LSP 与 tree-sitter**：这两个都需要额外进程或二进制依赖，本项目当前只处理自己的 Python 代码，`ast` 已经够用。**砍掉要写清楚**，不能让人以为"已经对齐原版"。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 文件数 | `code_index/` 14 | 计划 2（`indexer.py` + `query.py`） |
| 解析器 | LSP + tree-sitter + AST/javalang + 正则（四级） | 仅 Python `ast` |
| 语言 | Python / JS / TS / Java | 仅 Python |
| 导入绑定 | 三语言 `import_aliases_for_file` | 仅 Python |
| 引用抽取 | 三语言 `extract_internal_refs` | 仅 Python |
| 类型关系 | `enrich_type_relations`（含泛型拆解） | 不做 |
| 增量 | `CodeIndexWatcherRegistry` + `start_index_watch` | 不做，启动全量 |
| 向量 | `_load_sqlite_vec_extension` | 不做 |
| 库位置 | `_workspace_hash` 分库 | 工作区下单一 `index.db` |
| 结果排序 | `_symbol_rank` 定义优先 | 对齐 |
