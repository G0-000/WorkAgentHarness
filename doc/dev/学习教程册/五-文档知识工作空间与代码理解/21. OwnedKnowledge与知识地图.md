## 场景

用户点开自己的知识库，想看清"这批文档里到底讲了什么关系"：

- 哪个项目、哪个客户、哪个负责人被反复提到？
- "Phoenix-2" 和"续费率"之间，是通过哪几份文档连起来的？

这需要两样东西：

1. **实体关系**：从文本里抽出 `(主体, 关系, 客体)` 三元组，存成图；
2. **图的样子**：前端要能画出来——节点在哪、边连谁。浏览器不会自己算布局，后端得给一份"力导向载荷"。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 表结构随意扩展 | 14 张 `kb_*` 表各管一件事，缺一张就有一段流程断 |
| 索引管线同步阻塞 | 上传后界面卡死，看不到进度 |
| 图谱用图数据库 | 引入 Neo4j 依赖，部署成本翻倍 |
| 图谱查询只给节点 | 前端拿到孤立点，画不出关系 |
| 图载荷不设上限 | 一个 5000 节点的库，前端直接卡崩 |
| 图谱与 chunk 无关联 | 看到实体，但不知道它出自哪段文本 |

**图谱（`kg.py`，379 行）**：

| 符号 | 作用 |
|---|---|
| `:23` `_kg_conn(kb_id)` | 路由：`kb_*` 走该 KB 的索引库，`mem:*` 走中央库 |
| `:50` `upsert_node(...)`、`:115` `upsert_edge(kb_id, src_id, dst_id, rel_type)`、`:153` `add_triples(...)` | 写入 |

| `:215` `neighbor_chunk_ids(kb_id, node_ids, *, limit=40)` | 节点反查 chunk（**这就是"实体出自哪段"**） |

| `:369` `delete_by_kb`、`:375` `stats` | 清理与统计 |

**图谱抽取（`kg_pipeline.py`，172 行）**：`:26` `extract_triples_heuristic(text)`、`:160` `enqueue_kg_extract(...)`；文件头注释写明 "LLM (or heuristic) entity-relation extraction into SQLite"——**优先 LLM，退化用启发式**。

**知识地图的真实形状**：`graph_payload` 的 docstring 是 "Entity graph for force layout (G2)"——它返回的是**力导向布局**要的 nodes + edges；传 `center` 时只保留中心节点及其一度邻居，默认上限 80 个节点。

逐层追读要点：

1. **入口**：`run_parse_index` 由谁触发（上传后入队 / 手动重建）。
2. **调用者**：`enqueue_kg_extract` 在 pipeline 的哪个阶段被调用。
3. **核心决策**：`_norm_name` 怎么归一（小写？去空格？）；同名节点是合并还是新建。
4. **状态**：`kg_*` 表在**每个 KB 自己的索引库**里还是中央库——由 `_kg_conn` 的前缀路由决定。
5. **返回**：`graph_payload` 的 nodes / edges 字段。
6. **证据**：`neighbor_chunk_ids` 是"图 → 文本"的桥，没有它图谱就只是个孤立装饰。

## 调用流程

```text
文档入库
  ▼
① 解析切块    run_parse_index → kb_chunks
  ▼
② 抽三元组    enqueue_kg_extract → extract_triples_heuristic（或 LLM）
  ▼
③ 写图        _norm_name → upsert_node / upsert_edge / add_triples
  ▼
④ 关联文本    neighbor_chunk_ids：节点 → chunk 集合
  ▼
⑤ 图载荷      graph_payload(kb_id, center=..., limit=80) → nodes + edges
  ▼
⑥ 前端       力导向布局渲染"知识地图"
```

## WorkAgentHarness 现状与设计

**现状**：无知识库，无图谱。第 20 章的设计只到"向量 + 关键词检索"。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 表结构 | 5 张：`kb_documents`、`kb_chunks`、`kb_embeddings`、`kg_nodes`、`kg_edges` | 不做 folder / wiki / jobs / activity |
| 抽取 | 只做启发式：正则抽"《…》""「…」"和英文专名，产出 `(src, rel="提到", dst)` | 不接 LLM 抽取 |
| 归一 | `_norm_name`：小写 + 去首尾空格 + 全角转半角 | 不做同义词合并 |
| 关联 | `kg_node_chunks(node_id, chunk_id)` 关联表 | 对齐 `neighbor_chunk_ids` |
| 图载荷 | `graph_payload(kb_id, center, limit=80)` 返回 `{nodes, edges}` | 同上限 80 |
| 中心裁剪 | 传 `center` 时保留中心 + 一度邻居 | 对齐原版逻辑 |
| 后台作业 | 不做 | 索引同步执行 |

**为什么保留 `center` 裁剪**：一个真实知识库动辄几千节点，前端画不动。原版用 `center + 一度邻居 + limit` 收敛，本项目照抄这个思路——这是"图能看"和"图能崩"的分界线。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 文件规模 | `owned/` 29 文件 | 计划 5 文件 |
| 表 | 14 张 `kb_*` + `kg_*` | 5 张 |
| 抽取 | LLM + 启发式（`extract_triples_heuristic`） | 只有启发式 |
| 图谱存储 | SQLite（`kg_*`，无 Neo4j），按前缀路由 | SQLite 单库 |
| 图查询 | `find_nodes_by_query` / `search_graph_chunks` | 只做 `find_nodes_by_query` |
| 图→文本 | `neighbor_chunk_ids` | 关联表（同思路） |
| 可视化 | `graph_payload` 力导向载荷 | 同名同形状，limit 80 |
| 未做 | — | wiki、jobs、activity、doc_links、blob_store、builtin_seed |
