## 场景

一个功能三个人并行做，两小时后必然出现这些情况：

- A 说做完了，B 说还在做——**谁的状态是对的**？
- C 改了 A 依赖的文件，A 不知道——**冲突谁负责**？
- 中间断了，重启后 A 的进度**还在不在**？

"协作账本"解决的就是这些。它不是"把消息拼在一起"，而是**一份所有人共用的状态表**：谁在做什么、做到哪、卡在哪、下一步是什么。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 状态分散在各自对话里 | 谁说的都不算，冲突无人裁决 |
| 改派不留痕 | 不知道这块从谁手里转走的 |
| 无进度快照 | 用户问"做到哪了"答不出来 |
| 无健康检查 | 任务卡死无人发现 |
| 无回收机制 | 人走了，任务永远挂着 |
| 会议只是聊天 | 讨论完不落账，等于没开 |

## EvoFlow 源码阅读路径

`collab/` 按四组挑读（100+ 文件不可能全读）：

| 组 | 文件 | 作用 |
|---|---|---|
| ① 分工 | `task_assignee.py`、`agent_assignment.py`、`task_source.py`、`worker_tool_allowlist.py` | 派给谁、给什么工具 |
| ② 账本 | `state_transitions.py:108 can_transition(from, to)`；`:122 validate_transition`；`:136 get_allowed_transitions`；`task_state_service.py:58 class TaskStateService`；`:32 class TaskStatusChangeRecord(BaseModel)`；`subtask_state_machine.py:44 normalize_subtask_status`、`:51 is_terminal_subtask_status`、`:55 is_active_subtask_status`、`:59 can_advance_subtask_status` | 状态唯一来源 |
| ③ 任务中心 | `task_progress.py`、`task_progress_snapshot.py`、`task_runtime_health.py`、`task_reclaim.py`、`task_observability.py`、`work_checklist.py` | 进度、健康、回收、清单 |
| ④ 会议 | `thread_collab.py`、`conversation_scope.py`、`subtask_conversation.py`、`upstream_receipt.py`、`user_execution_confirm.py` | 多方对话与确认 |

**四个状态函数值得单独记**（`subtask_state_machine.py`）：
- `normalize_subtask_status(raw)`：脏数据归一（DB 里存了别名也能救）
- `is_terminal_subtask_status(status)`：终态判定
- `is_active_subtask_status(status)`：活跃判定
- `can_advance_subtask_status(...)`：能不能往前走

逐层追读要点：入口是任务创建；核心决策是 `can_transition` 的白名单；状态在 `TaskStatusChangeRecord` 留痕；返回是进度快照。

## 调用流程

```text
任务创建
  ▼
① 分工      task_assignee → 负责人 + worker_tool_allowlist
  ▼
② 记账      TaskStateService → can_transition 校验 → 改状态
  ▼
③ 留痕      TaskStatusChangeRecord（谁、从什么、到什么、为什么）
  ▼
④ 快照      task_progress_snapshot → 对外可查的进度
  ▼
⑤ 巡检      task_runtime_health → 卡死识别 → task_reclaim 回收
  ▼
⑥ 会议      thread_collab / subtask_conversation → 结论落回账本
```

## WorkAgentHarness 现状与设计

**现状**：没有协作。`sessions`/`messages`/`runs` 三张表只有单线程语义。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 账本 | 复用 `runs` 表加 `assignee` + `parent_run_id` 两列 | 不新建大表 |
| 状态机 | 五态 + `can_transition` 白名单（与 22 章共用） | 不重复定义 |
| 留痕 | `run_status_changes(run_id, from_status, to_status, reason, at)` | 单表 |
| 快照 | `task_progress_snapshot` → 直接从表算，不物化 | 不做缓存 |
| 健康 | 用 `updated_at` 超时判定（>10 分钟无更新 = 疑似卡死） | 不做心跳 |
| 回收 | 手动：把 `running` 且超时的改 `failed` | 不做自动回收 |
| 会议 | **不做** | 多方可视化不在本项目范围 |

**要写清的一条**：原版 `collab/` 100+ 文件里大量是"工作流应用（app_*）"和"多人会话"，这部分属于第 30 章与第十二篇，本章只看任务账本。**不分层读会把 100 个文件平铺，看不出结构**。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 账本规模 | 100+ 文件、多张任务/子任务表 | `runs` 加两列 |
| 状态归一 | `normalize_subtask_status`（脏数据可救） | 不做，写库前校验 |
| 留痕 | `TaskStatusChangeRecord` | `run_status_changes` |
| 健康检查 | `task_runtime_health` | `updated_at` 超时 |
| 回收 | `task_reclaim` 自动 | 手动 |
| 会议 | 完整多方会话 | 不做 |
