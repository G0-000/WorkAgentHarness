## 场景

一个任务跑了 40 分钟，进程被杀。重启后系统看到 `runs` 表里有一行状态是 `running`。

现在必须回答一个问题：**这条 running 是我这个进程在跑，还是上一个进程死了留下的尸体？**

- 如果是我的 → 继续，什么都不做；
- 如果已经死了 → 必须接手，否则这条永远卡在 `running`。

猜错的代价都很大：当成死尸接手 → 两个进程同时干同一件事，写冲突；当成活的不接手 → 任务永远卡住。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 只看 `status='running'` | 僵尸任务永远不被接手 |
| 无执行世代 | 分不清是谁写的 running |
| 重试不判幂等 | 同一封邮件发两次 |
| 无进展判定 | 任务活着但不动，也一直占着 |
| 恢复从头跑 | 40 分钟白费 |
| 回收太激进 | 真在跑的任务被误杀 |

| 层 | 文件与真实符号 | 作用 |
|---|---|---|
| ① 执行世代 | `collab/runner_epoch.py:50` `current_runner_epoch()`；`:42` `_env_epoch()`；`:46` `_boot_cycle_id()`；`:68` `runner_process_started_ts()` | **每次启动一个新 epoch** |
| ② 僵尸识别 | `collab/workflow_reconciler.py:60` `is_zombie_executing_subtask(...)`；`:32` `_auto_retry_max()`；`:38` `_stale_updated_seconds()` | 判断"执行中但已死" |
| ③ 陈旧回收 | `collab/task_reclaim.py:48` `_is_stale(task, *, days, now)`；`:55` `_progress(task)`；`:62` `_children_all_fully_closed(parent_task_id)` | **回收前先确认子任务全关** |
| ④ 状态迁移 | `collab/state_transitions.py:108 can_transition`；`subtask_state_machine.py:51 is_terminal_subtask_status` | 只有合法迁移才写 |
| ⑤ 续跑 | `collab/continue_subtask_session.py`；`collab/subtask_conversation.py` | 从会话继续 |
| ⑥ 租约 | `subagents/runtime_guard.py:21` `collab_subtask_lease_seconds(...)` | 防并行 |

**执行世代是怎么用的**（本条最值得记）：

```
启动 → current_runner_epoch() 生成新值（如 pid + 启动时间）
写任务 → 同时写入 runner_epoch=<当前值>
重启后 → 看到 status=running 且 runner_epoch != 当前值
         → 说明是上一代进程留下的，可判定为僵尸
```

`_is_stale` 还要看**进展**（`_progress`）和**子任务是否全关**（`_children_all_fully_closed`）——只看时间会误杀正在跑长任务的任务。

逐层追读要点：`_auto_retry_max` 与 `_stale_updated_seconds` 是两个阈值，**重试次数**和**陈旧时间**要一起判。

## 调用流程

```text
进程启动
  ▼
① 取世代    current_runner_epoch() → 新 epoch
  ▼
② 扫库      找 status=running 的行
  ▼
③ 判僵尸    runner_epoch != 当前 → is_zombie_executing_subtask
  │             ├ 是僵尸 → 走回收
  │             └ 是活的 → 跳过
  ▼
④ 判陈旧    _is_stale(时间 + _progress + 子任务全关)
  ▼
⑤ 回收      改状态（failed/timeout）→ 可重试
  ▼
⑥ 续跑      continue_subtask_session → 从断点继续
```

## WorkAgentHarness 现状与设计

**现状**：`run_repository` 有 `WHERE status='running'` 的幂等更新（第三篇已加注释），但**没有执行世代**——重启后无法判断 running 是真活还是尸体。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 执行世代 | `runner_epoch` 列 + 启动时算 `f"{pid}-{start_ts}"` 写入 | 对齐 `current_runner_epoch` |
| 僵尸判定 | `status='running' AND runner_epoch != current` → 判僵尸 | 不做子任务判定 |
| 陈旧 | `updated_at` 超 10 分钟 + 连续两次扫描无进展 | 简化 `_is_stale` |
| 回收 | 僵尸 → `failed`，附 `error_code="ZombieReclaimed"` | 不做自动重试 |
| 幂等 | 已有（`WHERE status='running'` 条件更新） | 保持 |
| 续跑 | **不做**，僵尸直接失败 | 明确写清不做 |
| 租约 | 不做（单进程） | — |

**必须写清楚**：本项目"回收"= 标记失败，**不是**自动接着跑。续跑需要计划与子任务表（22/23 章），当前都还没有。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 执行世代 | `current_runner_epoch`（env + boot cycle） | `pid-start_ts` |
| 僵尸判定 | `is_zombie_executing_subtask`（多条件） | epoch 不等即僵尸 |
| 陈旧判定 | 时间 + 进展 + 子任务全关 | 时间 + 两次无进展 |
| 自动重试 | `_auto_retry_max` | 不做 |
| 续跑 | `continue_subtask_session` | 不做 |
| 租约 | 有 | 不做 |
