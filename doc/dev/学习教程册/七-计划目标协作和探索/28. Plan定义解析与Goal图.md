## 场景

用户说："帮我做一个登录功能，前后端都要，还要写测试。"

Agent 要做的第一件事不是写代码，而是**拆**：

```
登录功能
├── 后端：/auth/login 接口
├── 前端：登录页 + 表单校验
└── 测试：接口用例 + 页面用例
```

拆完还要回答三个问题：
1. **哪些能并行**（前后端可以，测试要等）
2. **谁负责**（子代理 or 主 Agent）
3. **怎么算完**（每个子任务的验收条件）

这就是 Plan。没有 Plan，Agent 会边做边忘，做完一半才发现漏了测试。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 不做计划直接干 | 做到一半发现依赖没做，返工 |
| 计划存在对话里 | 上下文一压，计划丢了 |
| 没有依赖关系 | 测试先于实现跑，永远失败 |
| 没有验收条件 | "做完了"由 Agent 自己说了算 |
| 计划不可恢复 | 进程重启，从头再来 |
| 计划与执行两套状态 | 计划说"进行中"，实际已失败 |

## 调用流程

```text
用户需求
  ▼
① 生成计划    plan_session_task → 任务树（节点 + 依赖 + 验收）
  ▼
② 过闸门      supervisor_plan_gate → 计划合法才开工
  ▼
③ 落子任务    plan_subtasks_sync → 写子任务表
  ▼
④ 派发        task_assignee → 分配给子代理 / 主 Agent
  ▼
⑤ 改状态      TaskStateService → can_transition 校验
  ▼
⑥ 留痕        TaskStatusChangeRecord → 变更记录
```

## WorkAgentHarness 现状与设计

**现状**：没有计划。第三篇的 `goal_auto_continue.py` 只有一个 `MAX_STEPS=8` 的进程内计数器和 `_STEPS` dict，**不是任务计划**。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 计划结构 | `Plan` = `list[PlanNode]`，节点含 `id/title/deps/acceptance/assignee` | 不做树形嵌套，扁平 + `deps` |
| Goal 图 | 由 `deps` 算出拓扑序，同层可并行 | 复用现成的 Kahn 算法 |
| 落库 | `plan_nodes(plan_id, node_id, title, status, deps_json, acceptance)` | 单表 |
| 状态机 | 五态：`pending / running / done / failed / skipped` + `can_transition` 白名单 | 对齐原版思路 |
| 闸门 | 计划为空或存在环 → 拒绝开工 | 对齐 `supervisor_plan_gate` |
| 与 goal 的关系 | **不复用** `goal_auto_continue` 的 `_STEPS` | 写清两者不同 |

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| "Plan" 的含义 | `plans/` = 套餐授权；任务计划在 `collab/` | 只有任务计划，无套餐概念 |
| 计划生成 | `plan_session_task` 从会话推导 | 由模型直接输出结构 |
| 同步 | `plan_subtasks_sync` 双向 | 单向写表 |
| 闸门 | `supervisor_plan_gate` | 简单环检测 |
| 状态机 | `can_transition` 白名单 + `TaskStateService` | 同名白名单，无服务类 |
| 留痕 | `TaskStatusChangeRecord` | `plan_node_changes` 表 |
