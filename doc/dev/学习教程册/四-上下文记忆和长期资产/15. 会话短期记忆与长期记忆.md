## 场景

你在周一告诉 Agent："这个项目所有 Python 文件用 4 空格缩进，不要用 tab。"周三新开一个对话，它记住了，写代码直接对——这是**长期记忆**。

反过来，周三的对话里你说"这次先别看 tests 目录"，十分钟后你说"还是看一下吧"。它应该记住后者、忘掉前者——这是**短期记忆**，任务结束就该清掉。

最容易出的错是**把两者混在一起**：
- 短期内容写进长期 → 周一的偏好表里堆满"这次先别看 tests"这种一次性指令，越用越脏；
- 长期内容当成短期 → 每次新对话都得重新告诉它缩进规范。

## 本章要完成的功能

| 功能 ID | 要达成的行为 | 用户可见结果 |
|---|---|---|
| `WAH-MEM-002` | 短期记忆：按 thread 存任务内的对话摘要与临时事实 | 同一会话内不重复解释；换会话就清空 |
| `WAH-MEM-003` | 长期记忆：按 Agent 存稳定的用户偏好与项目规范 | 新会话自动带上，无需重述 |

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 没有 thread 维度 | 两个任务共用一份"临时事实"，互相污染 |
| 长期记忆无准入标准 | 什么都被当"事实"存进去，越积越乱 |
| 清理时机不明 | 任务结束了记忆还在，下次误用 |
| 记忆读出来不合并 | 上层要自己拼两份，容易漏 |
| 存储后端散乱 | 长期记忆分别落在 JSON、SQLite、知识库表里，迁移困难 |

## EvoFlow 源码阅读路径

**原版是"两级 + 单后端"**：两级按 `agent_name` / `thread_id` 分文件，后端统一走 `OwnedMemoryStorage`。

| 层 | 文件与真实符号 | 作用 |
|---|---|---|
| 长期（Agent 级） | `agents/memory/agent_memory.py:13` `class AgentMemoryManager`；`:34` `get_agent_memory_path()`；`:55` `load_agent_memory()`；`:72` `save_agent_memory(memory)`；`:157` `add_fact_to_agent_memory(fact, confidence=1.0)` | 跨会话的稳定事实 |
| 短期（Task 级） | 同文件 `:44` `get_task_memory_path(thread_id)`；`:88` `load_task_memory(thread_id)`；`:108` `save_task_memory(thread_id, memory)`；`:143` `clear_task_memory(thread_id)`；`:177` `add_to_task_history(thread_id, role, content)` | 任务内的对话与临时状态 |
| 合并视图 | `:125` `get_combined_memory(thread_id=None)` | 上层要一次性拿到两级 |
| 存储后端 | `agents/memory/storage.py:24` `get_memory_storage()`；底层 `evoflow/memory/storage.py` 的 `MemoryStorage` / `OwnedMemoryStorage` / `SqliteMemoryStorage` / `FileMemoryStorage` | 单例，**实际落在 Owned KB 的 `mem_*` 表**（文件头注释写明 "legacy evoflow_memory retired"） |

逐层追读要点：

1. **入口**：谁在会话开始时加载记忆、谁在轮次结束时保存。
2. **调用者**：`AgentMemoryManager` 是被中间件调，还是被 `make_lead_agent` 调。
3. **核心决策**：什么算"事实"、`confidence` 由谁给。
4. **状态**：两个 path 由什么拼出来（`agent_name` / `thread_id`），清理谁负责。
5. **返回**：`get_combined_memory` 的字段结构。
6. **证据**：`storage.py` 的注释说明后端已从文件迁到知识库表，这是可复核的迁移证据。

## 调用流程

```text
会话开始
  ▼
① 读长期    AgentMemoryManager.load_agent_memory()
  ▼
② 读短期    load_task_memory(thread_id)
  ▼
③ 合并      get_combined_memory(thread_id) → 注入提示词/上下文
  ▼
... 多轮对话 ...
  ▼
④ 轮次结束   add_to_task_history(thread_id, role, content)
  ▼
⑤ 发现稳定事实？ ── 是 ──→ add_fact_to_agent_memory(fact, confidence)
  │ 否
  ▼
⑥ 任务结束  clear_task_memory(thread_id)
```

## WorkAgentHarness 现状与设计

**现状**：本项目**没有记忆模块**。第三篇只做到"对话消息存在 SQLite（`SessionRepository` / `MessageRepository`）"，那是**业务记录**，不是"记忆"——它不做摘要、不做事实抽取、不跨会话复用。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 两级维度 | 长期用 `agent_name`（本项目只有 `default`），短期用 `thread_id` | 先单 Agent |
| 存储 | 复用现有 SQLite：新增 `agent_memory` / `task_memory` 两张表 | 不新建数据库 |
| 合并 | `get_combined_memory(thread_id)` 返回 `{long_term, short_term, merged}` | 字段名对齐原版 |
| 准入 | 只有"用户显式陈述 + 跨任务复用"才进长期 | 其他一律留短期 |
| 清理 | 任务完成回调里 `clear_task_memory` | 与 6.1 的 Run 生命周期绑定 |

**为什么复用 SQLite 而不是照搬知识库表**：本项目没有知识库（那是第五篇的事），先落 SQLite 才能在本篇内闭环。这是**有意识的偏差**，不是遗漏。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 长期维度 | `agent_name`，多 Agent 可切换 | 单 Agent（`default`） |
| 短期维度 | `thread_id` | `thread_id`（一致） |
| 存储后端 | `OwnedMemoryStorage` → 知识库 `mem_*` 表 | SQLite 两张新表（**有意偏差**） |
| 合并接口 | `get_combined_memory(thread_id=None)` | 同名设计，字段对齐 |
| 事实写入 | `add_fact_to_agent_memory(fact, confidence)` | 同名，但 `confidence` 先固定 1.0 |
| 清理 | `clear_task_memory(thread_id)` | 同名，挂在 Run 完成回调 |
| 迁移历史 | `storage.py` 注释：从 `evoflow_memory` 迁到 Owned KB | 无迁移，新建表 |
