## 场景

你让 Agent 做了一下午的活。结束时要交三样东西：

1. **产物**：它生成的报告、图表、改过的代码文件——你要能点开看，不是一段文字里说"我生成了 xxx"；
2. **事项**：这一轮做了什么、结果如何、有没有留尾巴（`wrap_up` 交班）；
3. **反思**：下次该注意什么——"上次这个仓库测试跑不起来，是因为缺 .env"。

这三样都不能塞回对话历史里（下轮就被压缩掉了），得有各自的位置和形状。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 产物只存在于对话文本里 | 下轮上下文一压，链接就没了 |
| 产物没有统一 id | 同一个文件每次生成都被当成新产物，前端重复显示 |
| 资产路径不按实体分 | 两个 Agent 写同名文件互相覆盖 |
| 路径没做安全校验 | `../../` 能写出自己的资产目录 |
| 反思只写在自然语言里 | 下次要用时无法检索 |

逐层追读要点：

1. **入口**：模型怎么调 `assets` 工具；`_resolve_entity` 从哪里拿身份（`runtime` 的 principal / agent）。
2. **调用者**：`wrap_up` 是 Agent 自己触发还是外层触发的阶段。
3. **核心决策**：`normalize_artifact_type` 如何从 path/mime 推断类型；`artifact_state_key` 用什么做去重键。
4. **状态**：产物 id 如何生成、上限 40 条是硬截断还是分页。
5. **返回**：`assets` 工具返回什么（路径？内容？引用？）。
6. **证据**：`sanitize_user_asset_id` 的哈希后缀是可复核的安全证据。

## 调用流程

```text
模型 tool_call: assets(mode=write, path="report.md", content=...)
  ▼
① 解实体      _resolve_entity(runtime) → EntityRef(user/agent/…)
  ▼
② 规范化路径   _normalize_asset_rel → sanitize_user_asset_id
  ▼
③ 算绝对路径   entity_root(entity) / workspace_asset_root
  ▼
④ 写入        （越界拒绝）
  ▼
⑤ 产物归一化   make_artifact_id(type, path, content) → normalize_chat_artifact
  ▼
⑥ 进消息       挂到 AI 消息的 artifacts（最多 40 条）
  ▼
⑦ 收尾交班     proactive_submit_work(phase="wrap_up", outcome, reflection, initiatives)
  ▼
⑧ 反思落库     Entity Asset Hub: experience / process / reflection / preferences
```

## WorkAgentHarness 现状与设计

**现状**：本项目**没有资产与产物模块**。第三篇的 `workspace_file.py` 只有 `read_text_file` / `list_directory`，**没有写能力**；CLI 只打印文本，不产出可点开的产物。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 资产目录 | `<cwd>/.wah/assets/{user,workspace}/`，两类 | 不做 `agent` / `employee` |
| id 安全 | 照搬 `sanitize_user_asset_id` 思路：非法字符替换 + 冲突时加 8 位 sha256 | 路径穿越仍是拒绝 |
| 产物形状 | `{id, type, name, path, size}`，`type` 由扩展名推断（md/png/json/log） | 对齐 `normalize_artifact_type` |
| 去重 | `artifact_state_key` = `type + path + size`，同键视为同一产物 | 不比内容 hash（成本高） |
| 条数上限 | 40 条，超出丢最早 | 对齐 `limit=40` |
| 事项/反思 | CLI 收尾时写一条 `wrap_up` 记录进 `run_wrapups` 表 | 不新建 Entity Asset Hub |
| 写能力 | **本章只设计不实现**；若要实现，先补 `write_text_file` + 审批 | 与 7.2"只读"的边界冲突需先解决 |

**顺序提醒**：产物要能"点开"，前提是有写文件和 HTTP 服务；这两个都在本篇之后的章节。所以本章按"设计先行"处理，不强行实现。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 实体类型 | 四类 `user/agent/employee/workspace` | 两类 `user/workspace` |
| 资产根 | `assets_root()` + `workspace_asset_root()` | `<cwd>/.wah/assets/` |
| 产物 id | `make_artifact_id(...)`（type/path/url/content/name 五因子） | 三因子 `type + path + size` |
| 产物归一化 | `normalize_chat_artifact` + `normalize_chat_artifacts(limit=40)` | 同名设计，字段简化 |
| 资产工具 | `tools/builtins/assets_tool.py` 的 `@tool("assets")` | 无（写能力未开） |
| 事项/反思 | `proactive_submit_work` + Entity Asset Hub 四类写入 | 单表 `run_wrapups` |
| `reflection` 同名 | `evoflow.reflection` 是 Python 反射；业务反思在工具参数 | 本项目无 `evoflow.reflection` 对应物 |
