## 场景

你在 CLI 里连着问了 30 轮，每轮都让 Agent 读几个文件。到第 25 轮左右，Agent 开始忘事：它不记得第一轮你定的命名规范，还把前面读过的文件又读了一遍。

更糟的是另一个场景：第 31 轮直接报错——**上下文塞满了**，模型拒绝请求。

本章要解决的就是这两件事：
1. 上下文快满了，怎么**在用户察觉前**把旧内容压掉；
2. 压掉之后，哪些东西**必须留下**（你定的规范、已经改过的文件），哪些可以丢（读过一遍的原文）。

## 本章要完成的功能

| 功能 ID | 要达成的行为 | 用户可见结果 |
|---|---|---|
| `WAH-MEM-001` | 上下文来源盘点与预算计算：知道这一轮请求到底占了多少 | 长对话不会突然报"超长" |
| `WAH-MEM-008` | 压缩后恢复：折叠发生在哪一步、折叠了几条、模型看到的是哪一版 | 折叠后能解释"Agent 为什么忘了某句" |
| `WAH-TOOL-007` | 工具历史合并与老化：重复读同一文件的 ToolMessage 合并 | 同一文件不会在上下文里出现五遍 |

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 按字符数估算，而模型按 token 计费 | 估算偏乐观，压得不够，仍然超限 |
| 压缩在前台同步做 | 每轮都多一次模型调用，用户等得更久 |
| 折叠时不分轻重 | 把你刚定的规范一起折掉，比不折更糟 |
| ToolMessage 越积越多 | 一个大文件读三遍，直接把预算吃光 |
| 折叠后没有标记 | 事后查不出"这轮为什么少了两条消息" |

## EvoFlow 源码阅读路径

**原版是"估算 → 入队 → 后台压缩 → 折叠 → 标记"五段**，不是一个中间件自己扛。

| 层 | 文件与真实符号 | 作用 |
|---|---|---|
| ① 预算估算 | `context/model_request_token_estimate.py:37` `class ModelCallOverheadEstimate`；`:112` `estimate_system_prompt_tokens(request, *, model=None)` | 算这一轮请求的 token 开销 |
| ② 压缩队列 | `context/context_compaction_queue.py:20` `class CompactionJob`；`:32` `class ContextCompactionQueue`；`:207` `get_context_compaction_queue()` | 把"要压"的任务入队，异步处理 |
| ③ 折叠执行 | `agents/middlewares/context_compaction_middleware.py`（1500 行）：`:89` `compaction_folded_this_call()`、`:93` `compaction_fold_msg_counts()`、`:97` `last_bound_model_messages()` | 真正的折叠动作与结果回读 |
| ④ Tool 历史治理 | `context/tool_history_merge.py:58` `class ToolRoundEntry`、`:108` `_eligible_cold_tool`、`:120` `_scan_cold_prefix`；`context/tool_history_ager_queue.py` | 冷的工具轮次合并/老化 |
| ⑤ 摘要与缓存 | `context/tool_result_summarizer.py`、`tool_summary_prompts.py`、`context_ref_lru.py`、`file_read_cache.py` | 把 Tool 结果换成摘要；读文件走 LRU |

逐层追读要点：

1. **入口**：谁在模型调用前算预算（不是用户触发，是请求装配处）。
2. **调用者**：谁把 job 放进队列、谁消费队列（前台 vs 后台线程）。
3. **核心决策**：折叠的阈值是什么、保留哪几条（`last_bound_model_messages` 读的就是"模型实际收到的那一版"）。
4. **状态**：job 存哪、折叠计数存哪、跨轮怎么读回来。
5. **返回**：折叠后如何通知上层"这次折了几条"。
6. **证据**：`compaction_fold_msg_counts()` 返回 `(before, after)`，这就是可观测证据。

## 调用流程

```text
模型请求装配
  ▼
① 估算 token     ModelCallOverheadEstimate / estimate_system_prompt_tokens
  ▼
② 超阈值？  ── 否 ──→ 直接请求
  │ 是
  ▼
③ 入队           ContextCompactionQueue.append(CompactionJob)
  ▼
④ 折叠           context_compaction_middleware.before_model
  │   · 保留最近 N 条
  │   · 老的替换成摘要
  │   · 合并同文件的 ToolMessage（tool_history_merge）
  ▼
⑤ 打标记         _mark_compaction_folded(before, after)
  ▼
⑥ 模型实际收到 last_bound_model_messages()
```

## WorkAgentHarness 现状与设计

**已经有的（第三篇 9.2，属于已有能力，不是本章成果）**：

| 项 | 现状 |
|---|---|
| 触发点 | `middleware/context_compaction.py:90` `before_model` |
| 阈值 | `MAX_CONTEXT_CHARS = 12000`（**字符**，不是 token） |
| 保留条数 | `KEEP_RECENT_MESSAGES = 6` |
| 折叠方式 | `_fold_summary` 把老消息压成一条本地摘要文本 |
| 计数 | `_total_chars` 统计当前长度 |

**本章要补的设计（只写方案，不写代码）**：

| 缺口 | 设计方案 | 为什么这样 |
|---|---|---|
| token 估算 | 引入可插拔 `estimate_tokens(text)`，默认按 `len(text)//3` 近似，接口留 tokenizer 位置 | 不引第三方 tokenizer 也能跑，日后可替换 |
| 异步压缩 | 先做"标记待压 + 下一轮开头处理"，不引入线程池 | 单进程 CLI 下线程池收益低，复杂度高 |
| 分级保留 | 给消息打 `pinned`（用户显式规范、已改文件路径），折叠时跳过 | 这几类丢了最伤 |
| Tool 合并 | 同 `tool_call_id` / 同文件路径的旧 ToolMessage 只留最后一次 | 重复读是最大浪费 |
| 折叠可观测 | 记录 `(before, after)` 并写进事件 | 事后能回答"为什么少了两条" |

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 预算口径 | token（`ModelCallOverheadEstimate`） | 字符（`MAX_CONTEXT_CHARS=12000`） |
| 压缩时机 | 队列 + 后台（`ContextCompactionQueue`） | 同步，`before_model` 内直接折 |
| 折叠实现 | 1500 行中间件，含分级、冷却、多轮 | 单函数 `_fold_summary` |
| Tool 历史 | `tool_history_merge.py`（299 行）+ 老化队列 | 无 |
| 摘要来源 | 模型生成（`tool_result_summarizer.py` + `tool_summary_prompts.py`） | 本地拼接文本，无模型调用 |
| 缓存 | `context_ref_lru.py`、`file_read_cache.py` | 无 |
| 可观测 | `compaction_fold_msg_counts()` | 只有内部 `_total_chars` |

**一句话差异**：原版是"预算驱动的异步压缩系统"，本项目是"字符阈值触发的同步折叠"。前者面向多用户长会话，后者够 CLI 自用。
