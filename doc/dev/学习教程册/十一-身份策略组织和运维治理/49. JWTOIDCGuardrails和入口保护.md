## 场景

第 48 章决定了"谁能看什么"。这一章回答"**怎么证明你是你**"，以及"**进来之后怎么管住**"。

两层：

1. **认证（AuthN）**：密码 / JWT / 单点登录（OIDC）。证明"你是张三"。
2. **护栏（Guardrails）**：进来之后，模型输入输出、工具调用要过一道策略。拦住"把 API key 说出来""执行危险命令"。

这两层经常被混为一谈。它们不一样：认证在门口，护栏在屋里。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 密码明文存 | 泄漏即全丢 |
| JWT 不校验过期 | 旧 token 永远有效 |
| OIDC 配置写死 | 换 IdP 要改代码 |
| 无护栏 | 模型把内部提示词吐出来 |
| 护栏做成"事后审计" | 危险动作已经执行完才发现 |
| 允许清单过宽 | 等于没有护栏 |

## EvoFlow 源码阅读路径

| 层 | 文件与真实符号 | 作用 |
|---|---|---|
| ① 密码 | `webui/auth.py:59` `hash_password(password)`；`:78` `verify_password(password, stored_hash)`；`:103` `generate_password(length=20)` | 哈希 / 校验 / 生成 |
| ② JWT | `:133` `generate_jwt(...)` | 签发 |
| ③ OIDC 配置 | `webui/oidc_config.py` | IdP 参数 |
| ④ OIDC 流程 | `webui/oidc.py` | 授权码流程 |
| ⑤ 中间件 | `webui/middleware.py` | 请求级拦截 |
| ⑥ 护栏提供方 | `guardrails/provider.py`、`:6` `class AllowlistProvider`（在 `guardrails/builtin.py`） | **允许清单** |
| ⑦ 护栏中间件 | `guardrails/middleware.py` | 在链路里拦截 |

**`AllowlistProvider` 是护栏的核心形态**：不是"黑名单拦危险词"，而是"**只有清单里的才放行**"。黑名单永远漏，白名单默认安全。

逐层追读要点：`hash_password` / `verify_password` 成对；`oidc_config` 与 `oidc` 分开说明"配置"和"流程"解耦。

## 调用流程

```text
① 登录
  用户名 + 密码 → verify_password → generate_jwt → 返 token
  ▼
② 携带 token 请求
  middleware 解析 → 校验签名 + 过期
  │   └ 失败 → 401
  ▼
③ OIDC（可选）
  跳 IdP → 回调 code → 换 token → 建立本地会话
  ▼
④ 进护栏
  请求/工具调用 → AllowlistProvider → 不在清单 → 拒绝并说明
  ▼
⑤ 执行
```

## WorkAgentHarness 现状与设计

**现状**：无认证、无护栏。CLI 无登录概念。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 密码 | **不做**（无多用户） | — |
| JWT | 不做 | — |
| OIDC | 不做 | — |
| 护栏（输入） | 关键词表：命中即拒（如"忽略之前的指令"） | 黑名单式，明确标注弱于白名单 |
| 护栏（工具） | **复用第 26 章的审批三档** `allow/ask/deny` | 这是已有的最强护栏 |
| 护栏（输出） | 正则扫 API key 形态（`sk-` / `ghp_` 前缀） | 三类前缀 |

**要写清的一条**：本项目护栏是**黑名单式**（关键词 + 输出扫描），原版是**白名单式**（`AllowlistProvider`）。黑名单必然漏，这是已知差距。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 密码/JWT | `webui/auth.py` 四函数 | 不做 |
| OIDC | `oidc.py` + `oidc_config.py` | 不做 |
| 护栏模型 | 白名单（`AllowlistProvider`） | 黑名单（关键词） |
| 护栏位置 | `guardrails/middleware.py` 链路拦截 | 入口函数 + 工具审批 |
| 输出扫描 | 未核实到 | 自造（三类前缀） |
