## 场景

同一个 Agent，用户在三个地方找它：飞书群里 @ 它、企业微信里发文件给它、网页里打字给它。

早上九点，飞书群来了三条消息：一条文字、一张截图、一个文件。Agent 要按顺序处理，先把图片存下来、把文件落盘，再合并成一轮对话回答。

下午，运营给每个员工配了一个独立的企微机器人。三个 bot 都叫 `wecom`，同一个 `channel_name`。

问题来了：如果出站回调只按 `channel_name` 存一个，那么第三个 bot 启动时会把前两个的回调覆盖掉——员工 A 的提问，回复可能从员工 C 的 bot 发出去。

这就是本章第一条硬约束的由来：**出站订阅必须按 `(channel_name, account_id)` 分开存**。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 每个渠道各写一套收发 | 六份代码，改一处漏五处 |
| 入站格式不归一 | Agent 要处理六种消息结构 |
| 出站回调只按渠道名存 | 同名多 bot 互相覆盖，回复串号 |
| 入站媒体不落盘 | 平台链接过期后图片变裂图 |
| 无 I/O 日志 | 消息丢了不知道丢在哪一段 |
| 无会话/线程绑定 | 同一个群的消息进不了同一个 thread |
| 无忙碌判定 | 上一轮没跑完又来一条，两轮交叉 |

## 调用流程（真实）

```text
【入站】
飞书/企微/微信/钉钉/Slack/Telegram 事件
  ▼
① 渠道实例解析        Channel 子类：raw → InboundMessage
  │  飞书三件套：feishu_inbound_parse → feishu_inbound_media → feishu_inbound_merge
  │  媒体落盘            inbound_media_store.py
  ▼
② 入队                MessageBus.publish_inbound(msg)
  │                      ├ channel_io_log.log_channel_inbound(msg)   ← 先记日志
  │                      └ asyncio.Queue.put(msg)
  ▼
③ 分发器取            ChannelManager ← MessageBus.get_inbound(timeout)
  ▼
④ 会话判定            _resolve_session_layer(msg) / _account_session(channel, account_id)
  │                      ├ 已绑定 thread → _lookup_bound_thread_id(msg)
  │                      └ 新会话 → 建/取 account session
  ▼
⑤ 忙碌闸门            _try_claim_chat_turn(_chat_lock_key(msg))
  │                      失败 → _im_turn_is_busy(msg) → 走忙时分支（不并发跑两轮）
  ▼
⑥ 跑 Agent            Gateway 聊天链路 → Agent → 工具 → 结果
  ▼
⑦ 发出站              MessageBus.subscribe_outbound 注册的回调
  │                      按 (channel_name, account_id) 取，不是按 channel_name 取
  ▼
⑧ 渠道发送            Channel.send(OutboundMessage) / send_file(...)
  │                      ├ _diag_outbound_enter   ← 出站前记
  │                      └ _diag_outbound_done    ← 出站后记成败
  ▼
⑨ 释放                _release_chat_turn(key)
```

第 ⑦ 步是本章最关键的一步。注释写在 `message_bus.py` 里：多个 IM 账号可能共用同一个 `channel_name`（主 bot + 每员工 bot 都叫 `wecom`），每个实例必须拥有自己的回调，否则最后启动的那个会把前面的覆盖掉，回复就由"最后启动的 bot"发出去。所以 `_outbound_by_account` 的键是元组 `(channel_name, account_id)`，重启一个实例只替换自己那一格。

## WorkAgentHarness 现状与设计

**现状**：只有 CLI 和 stdio 入口，**没有任何渠道**。`WAH-API-005–007` 全部未实现。

不按原版六个渠道铺开，先做一个渠道把链路跑通，再谈扩展。

| 组件 | 本项目设计 | 与原版对应 | 边界 |
|---|---|---|---|
| 抽象基类 | `Channel(ABC)`：`start()` / `stop()` / `send(msg)` | 对齐 `base.py:50` | 不做 `send_file` |
| 消息模型 | `InboundMessage(channel, account_id, chat_id, user_id, text, msg_id)` / `OutboundMessage(channel, account_id, chat_id, text, is_final)` | 精简版 `message_bus.py:31/90` | 不做附件与 thread_ts |
| 总线 | `MessageBus`：`publish_inbound` / `get_inbound` / `subscribe_outbound(..., channel_name, account_id)` | 对齐 `message_bus.py:130` | **必须保留 account_id 维度**，这是原版踩过的坑 |
| 队列 | `asyncio.Queue` | 对齐 | 只在进程内，不持久化 |
| 分发器 | `ChannelManager`：取入站 → 跑 Agent → 发出站 | 对齐 `manager.py:1870` 的最小子集 | 不做会话层、流式判定、线程绑定 |
| 轮次锁 | 按 `chat_id` 的进程内 dict | 对齐 `_try_claim_chat_turn` 思路 | 不跨进程 |
| I/O 日志 | 入站/出站各写一行到日志 | 对齐 `channel_io_log` | 不落库 |
| 渠道实现 | **只做 1 个**：`WebhookChannel`（接收 HTTP POST、回 HTTP） | 原版六渠道的极简版 | 不做飞书/企微/微信/钉钉 |
| token / 限流 | 不做 | 原版在各自渠道内处理 | 明确未实现 |
| 渠道健康 | 一行"最后成功时间 / 最后错误" | 原版有诊断日志 | 不做健康表 |

**本章真正要学的是三件事**，不是"接了几个渠道"：

1. **归一的边界在哪**——入站结构必须先归一，否则 Agent 侧要处理 N 种格式。
2. **出站按什么维度路由**——按 `(渠道, 账号)`，不是只按渠道。这一条不做，多 bot 场景必然串号。
3. **I/O 日志先于业务**——入队前先记账，否则消息丢了无法定位丢在解析、入队还是分发。

## 与 EvoFlow 的差异

| 项 | EvoFlow（`1e393d9dfba9`） | 本项目 |
|---|---|---|
| 渠道抽象 | `Channel(ABC)`，三抽象方法 + `send_file` | 同名同职责，去掉 `send_file` |
| 渠道数量 | 飞书、企微、微信、钉钉、Slack、Telegram 六个 | 1 个 `WebhookChannel` |
| 消息模型 | 四类（`InboundMessageType`/`InboundMessage`/`ResolvedAttachment`/`OutboundMessage`） | 两类，无附件 |
| 总线出站键 | `(channel_name, account_id)` | **保持一致**（关键对齐点） |
| 分发器 | `ChannelManager` 3956 行，含会话层、轮次锁、流式、线程绑定 | 最简子集，仅轮次锁 |
| 入站媒体 | `inbound_media_store.py` 落盘 | 不做 |
| 飞书三件套 | `feishu_inbound_parse/media/coalesce` + `trace_log` | 不做 |
| I/O 日志 | `channel_io_log.py` | 一致，只写文本日志 |
| token / 限流 / 健康 | 各渠道内 + 诊断脚本 | 不做，明确列为未实现 |
| 渠道注册 | `*_registration.py` 四个 | 不做 |

**差异说明单独成段**：上表"不做"的四项不是"原版没有"，是**本项目按教学规模裁剪**。写文档时不能因为本项目没做就写成"原版不存在"——这正是本章早期版本犯过的错。
