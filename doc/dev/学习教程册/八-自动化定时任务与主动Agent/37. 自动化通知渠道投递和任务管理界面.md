## 场景

第 36 章的巡检发现了 3 个超时工单。现在要送到用户眼前，有两条路：

1. **推消息**：飞书/企业微信里发一条"有 3 个工单超时，点这里处理"；
2. **进任务中心**：用户打开界面，看到一条待办，处理完标记完成。

只做第 1 条，用户没看到就等于没提；只做第 2 条，用户不主动开界面就永远不知道。**两条都要有，而且要能对上**——点了飞书里的按钮，任务中心那条要变成"已处理"。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 不判"是否退出渠道" | 用户退订了还推 |
| 目标不解析 | 推给空 target，静默失败 |
| 渠道写死 | 只能飞书，换企微要改代码 |
| 推送与待办两套状态 | 飞书点完了，任务中心还是"待处理" |
| 待办无进度 | 分不清"刚开始"和"快完" |
| 完成判定只看 status | 进度 80% 但 status=closed，到底算不算完 |

## 调用流程

```text
巡检产出待办（第 36 章）
  ▼
① 建待办      items → 状态 pending
  ▼
② 选渠道      _approval_channels(role) → [feishu, wecom]?
  ▼
③ 判退订      _feishu_channel_not_opted_out(role) → 退出则不推
  ▼
④ 解析目标    _outbound_feishu_target → resolve_role_feishu_target
  ▼
⑤ 推送        发送（带待办 id）
  ▼
⑥ 用户操作    点"处理" → 回调带 id
  ▼
⑦ 状态回写    items 状态变更 → is_work_item_done(status, progress)
  ▼
⑧ 界面同步    任务中心列表刷新
```

## WorkAgentHarness 现状与设计

**现状**：无通知、无任务中心。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 渠道 | 只做 **webhook 一种**（`webhook_url` 存在配置里） | 不接飞书/企微 SDK |
| 退订 | 配置里 `enabled=false` 即不推 | 对齐退订思路 |
| 目标 | webhook 不需要 target，只校验 URL 合法 | 简化 |
| 待办 | `work_items(id, title, source, status, progress, created_at, closed_at)` | 单表 |
| 完成判定 | `is_done = status in (closed, done) and progress >= 100` | 对齐 `is_work_item_done` |
| 界面 | **不做**（无 Web） | 只有 CLI 列表 |
| 回写 | 不做回调，CLI 里手动标记 | 无 HTTP 回调 |

**必须写清**：本项目**没有 UI** 也没有**回调**。"任务管理界面"这一半原版能力，本项目只有"CLI 列待办 + 手动改状态"。差异表要老实写。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 渠道数 | 飞书 + 企微 + 绑定仓库 | webhook 一种 |
| 退订 | `_feishu_channel_not_opted_out` | 配置开关 |
| 目标解析 | 三层函数 | 无（URL 直发） |
| 推送策略 | `push_policy` | 开关 |
| 待办 | `items/` 三文件（models/service/store） | 单表 |
| 完成判定 | `is_work_item_done(status, progress)` | 同思路 |
| 界面 | 完整任务中心 | 仅 CLI 列表 |
| 回调 | 有 | 不做 |
