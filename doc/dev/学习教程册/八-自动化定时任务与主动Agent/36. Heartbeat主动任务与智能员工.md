## 场景

第 34、35 章是"用户说了才做"。本章反过来：**用户没说，Agent 自己看有没有事**。

比如一个"客服值守"角色，每 30 分钟做一次：

1. **看**：有没有新工单没人接？有没有差评没回？
2. **判**：要不要打扰人？（"有 3 个工单超时" 值得说；"一切正常" 不值得说）
3. **做**：能自己处理的就处理，处理不了就提一条"待办"。

这里的核心不是"定时"，而是**决策闸门**：没有闸门，它每 30 分钟发一条"一切正常"，两天就被用户关掉。

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 巡检无闸门 | 没事也发消息，用户很快静音 |
| 无名额上限 | 一次巡检提 20 条建议，没人看 |
| 巡检无角色概念 | 不知道"谁"在巡逻，责任不清 |
| 不判执行失败 | 巡检自身失败也算"没问题" |
| 同日重复巡检 | 一天跑 48 次，重复提同一条 |
| 无 KPI 约束 | 主动提的事情没人跟，越积越多 |

**`round_token` 是最容易被忽略的一个**：它给"这一轮"一个标记，用来判断"这条建议是不是这一轮已经提过"。没有它，同一天会重复提 48 次同一个问题。

逐层追读要点：入口是 tick；核心决策是 `DecisionGate`（说/不说）；上限是 `effective_max_initiatives`（说几条）。

## 调用流程

```text
tick 到（30 分钟）
  ▼
① 建巡检记录  start_duty_run
  ▼
② 收集信息    工单 / 差评 / 任务 / 消息
  ▼
③ 决策闸门    DecisionGate → 这次值得说吗
  │              ├ 不值得 → 直接收尾（status=idle）
  │              └ 值得 → 继续
  ▼
④ 限额        effective_max_initiatives → 最多 N 条
  ▼
⑤ 去重        round_token → 本轮已提过的不再提
  ▼
⑥ 产出        工作项 / 通知（第 37 章）
  ▼
⑦ 收尾        update_duty_run（结果 + 提了几条）
```

## WorkAgentHarness 现状与设计

**现状**：无主动能力。Agent 只在用户输入时动。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 巡检循环 | 复用第 35 章的 tick（30 分钟） | 不做多角色 |
| 决策闸门 | 三条规则：有新工单 / 有失败任务 / 有超期项 → 说话；否则 `idle` | 不用模型判断 |
| 名额 | 每轮最多 3 条 | 对齐 `effective_max_initiatives` 思路 |
| 去重 | `round_token = 日期 + 小时段`，同 token 已提过的跳过 | 对齐 `round_token` |
| 记录 | 复用 `automation_runs`，`kind="heartbeat"` | 不新建表 |
| 失败判定 | 巡检执行抛异常 → `status=failed`，不当作"没事" | 对齐 `_is_execution_failure` |
| 角色/KPI | **不做** | 无多员工概念 |

**要写清的一条**：本项目的闸门是**规则式**（三条 if），原版是类 + 时间解析的完整对象。规则式更简单但更容易误判——这是有意识的简化。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 引擎 | `ProactiveEngine` 类 | 函数式巡检 |
| 闸门 | `DecisionGate` 对象 | 三条规则 |
| 名额 | `effective_max_initiatives(role)` | 固定 3 |
| 去重 | `round_token` + `round_refs` | `日期+小时段` |
| 角色 | 部门/组织/员工提示词 | 不做 |
| KPI | `kpi_checker` | 不做 |
| 巡检记录 | `duty_runs` | 复用 `automation_runs` |
