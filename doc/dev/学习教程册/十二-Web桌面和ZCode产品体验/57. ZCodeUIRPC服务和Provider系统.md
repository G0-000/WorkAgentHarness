## 场景

有些场景**不能起 HTTP 端口**：

- 桌面客户端内嵌后端，端口冲突概率高；
- 编辑器插件（VSCode 类），宿主进程已有自己的 IPC；
- CI 环境，端口管理麻烦。

解决办法：**stdio RPC**——父子进程通过标准输入输出传 JSON-RPC。

这和"MCP 的 stdio"是同一个思路，但这里传的不是工具调用，而是**一整套 UI 需要的数据**（会话、设置、任务、状态）。

## EvoFlow 源码阅读路径

| 层 | 文件与真实符号 | 作用 |
|---|---|---|
| ① RPC 服务 | `app_server/stdio_rpc.py:26` `class StdioAppServer`；`:503` `serve_stdio(...)`；`:684` `main_argv(argv)` | **服务主体 + 启动入口** |
| ② 编码 | `:486` `_force_utf8_stdio(stream)` | 强制 UTF-8 |
| ③ 扩展注册 | `admin/ui_extensions_registry.py:39` `_home()`；`:27` `ExtensionValidationError(ValueError)`；`:31` `ExtensionNotFoundError(LookupError)`；`:35` `ExtensionIOError(RuntimeError)` | 注册 + 三类错误 |
| ④ Provider | 供应商配置在 `config/`（第 3 章已读过 `model_config.py`），UI 侧通过 admin 页读写 | 配置面 |

**`_force_utf8_stdio` 是必踩的坑**：Windows 控制台默认不是 UTF-8，stdio 传中文会乱码。这个函数在 `main_argv` 之前就要执行。

逐层追读要点：先看 `main_argv`（命令行参数怎么定），再看 `serve_stdio`（循环怎么起），最后看 `StdioAppServer` 的方法分发。

## 调用流程

```text
宿主启动子进程
  ▼
① 参数解析    main_argv(argv) → 配置
  ▼
② 编码设置    _force_utf8_stdio(stdin/stdout)
  ▼
③ 起服务      serve_stdio(server) → 读一行 → 分发 → 写一行
  ▼
④ 方法分发    StdioAppServer → 按 method 名找处理函数
  ▼
⑤ 返回        JSON（含 code / data / error）
  ▼
⑥ 扩展页      ui_extensions_registry 注册 → 校验 → 挂载
```

## WorkAgentHarness 现状与设计

**现状**：
- `app_server/sse.py` 有 SSE 构造，但**没有 stdio RPC**。
- `cli/main.py` 是唯一下载入口（`main` / `open_checkpointer` / `make_lead_agent`）。
- `WAH-TOOL-009` 未实现。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| stdio RPC | **不做** | 无宿主客户端 |
| 编码 | 若做，读第一行前设 `sys.stdin.reconfigure(encoding='utf-8')` | 对齐 `_force_utf8_stdio` |
| 方法分发 | 若做，dict 表 `{"sessions.list": fn, ...}` | 不用 if-else |
| 错误码 | 若做，`{code, message}` 两字段 | 对齐扩展三类错误思路 |
| UI 扩展 | 不做 | — |
| Provider 面 | 不做（配置走文件，第 3 章） | — |
| ZCode 桥 | **不做**（`WAH-TOOL-009` 保持未实现） | — |

**必须写清**：本章 **4 个功能全部不做**。写它的目的是"知道还有 stdio 这条路"，不是"我们要实现"。
