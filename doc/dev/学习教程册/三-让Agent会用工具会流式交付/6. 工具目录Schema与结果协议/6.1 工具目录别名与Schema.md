# 第 6 章 · 第 1 节｜工具目录、别名与 Schema

## 场景

你开一家餐厅。后厨有炒锅、蒸箱、切菜台。你不能让服务员直接冲进厨房随便拿锅——得有一份**菜单**，上面写清楚"能做哪些菜、每道菜要什么配料"。客人（模型）看着菜单点菜，后厨按单子做。

这一节做的事一样：给模型一份"菜单"（工具目录）。目录里写着每个工具叫什么、干什么用、需要什么参数。模型只能从菜单里点，不能凭空发明一个工具。

## 这一节要实现什么功能

建一个工具登记表：注册时校验重名与别名冲突，对外给两种视图（模型看的 schema、人看的描述），支持别名解析，并把工具列表交给 Agent。

**可验收的行为**：`--once "计算 1+1"` 触发 calculator；注册同名工具或重复别名时 `ValueError`；`resolve("calc")` 能命中 `calculator`。

## 本节业务问题

模型要调用工具，必须先知道"有哪些工具、各自要什么参数"。这个信息不能散落在代码各处，也不能在提示词里手写一遍（会和真实工具实现脱钩）。

需要一份**工具目录**：
- 统一注册，重名不允许
- 别名能解析到同一个实现（`calc` 和 `calculator` 是同一个）
- 能导出 Schema 给模型
- 能导出元数据给 UI/日志

## 调用流程

```text
default_catalog()
  ▼

  ├─ 重名检查：已存在 → ValueError
  └─ 别名索引：_alias_index["calc"] = "calculator"

  ▼

```

## 关键函数与知识点

### `ToolCatalog.register`（catalog.py）

```python
def register(self, tool, *, tier="core", aliases=(), source="builtin"):
    name = tool.name
    if name in self._entries:
        raise ValueError(f"工具已存在，拒绝重复注册: {name}")
    entry = ToolEntry(tool=tool, tier=tier, aliases=aliases, source=source)
    self._entries[name] = entry
    for alias in aliases:
        if alias in self._alias_index:
            raise ValueError(f"别名冲突: {alias}")
        self._alias_index[alias] = name
    return entry
```

1. **重名直接报错**：不允许"后注册的覆盖先注册的"。工具重名会让模型调到意料之外的实现，这是静默故障，比启动失败更危险。
2. **别名唯一**：`calc` 只能指向一个工具；两个工具都想要 `calc` 时，第二个注册失败。
3. **注册顺序稳定**：`langchain_tools()` 按注册顺序返回，多次启动 schema 顺序一致，便于对比。

### 两个视图：模型看什么，UI 看什么

```text
schemas()        → 模型侧：{name, description, args(JSON Schema)}
describe_all()   → UI 侧：  {name, tier, source, aliases, description}
```

- **模型只需要"能干什么、要什么参数"**，不需要知道 tier 和来源。
- **UI/日志需要"这个工具哪来的、有哪些别名"**，用于工具面板和排查。
- 两个视图从同一份 `ToolEntry` 派生，不会出现"UI 显示有工具、模型却看不到"的漂移。

### 别名解析的两种语义

| 方法 | 找不到时 | 适用场景 |
|---|---|---|
| `resolve(name)` | 返回 `None` | 用户输入、配置里写别名，允许失败 |
| `get(name)` | 抛 `KeyError` | 代码内部装配，早失败早发现 |

### Schema 长什么样

```json
{
  "name": "calculator",
  "description": "计算数学表达式。支持 + - * / ** % 和括号，例如 \"(3+4)*2\"。",
  "args": {
    "properties": {"expression": {"title": "Expression", "type": "string"}},
    "required": ["expression"],
    "type": "object"
  }
}
```

模型看到的就是这段 JSON。`description` 写得好不好，直接决定模型会不会在正确时机调用它。
