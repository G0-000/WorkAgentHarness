# 第 10 章 · 第 1 节｜流事件生产

## 场景

你看视频直播。主播说话是一句一句出来的，你能看到他正在说话；如果等整场播完才给你看，那不叫直播，叫录播。

这一节做的事一样：Agent 干活时，把过程"一句一句"发出来——模型开始说话、调用工具、工具返回、回答结束。前端能边收边渲染，用户看到的是"正在打字"，不是长时间白屏后突然蹦出一整段。

## 这一节要实现什么功能

把 Agent 内部过程翻译成稳定事件：文本增量、工具调用、工具结果，再由运行器补上开始与结束事件。

**可验收的行为**：`--stream --once "计算 6*7"` 依次看到 `[工具调用] calculator`、`[工具结果] calculator ok=True`、最终答案 42。

## 本节业务问题

同步调用有三个体验问题：

1. **长时间白屏**：Agent 调三个工具要 10 秒，用户这 10 秒什么都看不到。
2. **不可观察**：用户不知道 Agent 在干什么（在算？在找文件？卡住了？）。
3. **无法中断判断**：用户不知道进展，也不知道该不该等。

需要一层"事件流"：把 LangGraph 内部输出翻译成前端能理解的稳定事件。

## 涉及文件

| 文件 | 职责 |
|---|---|
| `events/stream.py` | `stream_agent_run`：LangGraph chunk → 事件字典 |
| `events/__init__.py` | 导出 `Event` / `stream_agent_run` |
| `execution/run_service.py` | `execute_stream`：把事件流包进 run 生命周期 |
| `cli/main.py` | `--stream`：终端消费事件并即时打印 |

## 调用流程

```text
RunService.execute_stream(owner_id, session_id, text)
  ▼
runs.start → yield run_start
  ▼
sessions.add_message(user)
  ▼
stream_agent_run(agent, [("user", text)], thread_id=session_id)
  ├─ agent.stream(stream_mode=["messages","updates"])
  │
  ├─ messages 模式
  │    └─ AIMessageChunk content 非空 → yield text_delta
  │
  ├─ updates 模式
  │    ├─ AIMessage 带 tool_calls → yield tool_call(name, args)
  │    └─ ToolMessage → yield tool_result(name, ok)
  ▼
RunService 拼接收到的 text_delta → answer
  ▼
sessions.add_message(assistant) → runs.complete → yield run_end(completed)
```

## 代码走查：每一步走哪里

| 步 | 做什么 | 文件 | 类 / 函数 | 方法 / 调用 |
|---|---|---|---|---|
| 1 | 入口选择流式 | `cli/main.py` | `main()` | `--stream` → `_execute_stream_and_print(...)` |
| 2 | 进入用例层 | `execution/run_service.py` | `RunService.execute_stream(owner_id, session_id, text)` | `yield run_start` → 写 user 消息 |
| 3 | 订阅图输出 | `events/stream.py` | `stream_agent_run(agent, input_messages, thread_id)` | `agent.stream(..., stream_mode=["messages","updates"])` |
| 4 | 文本增量 | `events/stream.py` | `stream_agent_run` | `mode=="messages"` 且 `AIMessageChunk` → `yield text_delta` |
| 5 | 工具调用 | `events/stream.py` | `stream_agent_run` | `mode=="updates"` 且 `AIMessage.tool_calls` → `yield tool_call` |
| 6 | 工具结果 | `events/stream.py` | `stream_agent_run` + `_tool_result_ok(message)` | `ToolMessage` → `ok = not content.startswith("[")` → `yield tool_result` |
| 7 | 拼接回答 | `execution/run_service.py` | `RunService.execute_stream` | 收集 `text_delta` → `"".join(...)` |
| 8 | 落库与终态 | `execution/run_service.py` | `RunService.execute_stream` | `add_message(assistant)` → `complete(run_id)` → `yield run_end` |

## 关键函数与知识点

### 为什么要 `stream_mode=["messages", "updates"]`

| 模式 | 给什么 | 用途 |
|---|---|---|
| `messages` | 模型 token 增量 | 打字机效果 |
| `updates` | 每个节点的状态变更 | 工具调用/结果、步骤变化 |

只订阅 `messages` 会漏掉工具事件；只订阅 `updates` 会失去逐字效果。两个一起订阅，才能同时做到"文字流"和"工具活动"。

### 事件翻译，不是透传

```python
# LangGraph 原始 chunk
("messages", (AIMessageChunk(content="你"), {"langgraph_node": "model"}))
("updates", {"tools": {"messages": [ToolMessage(content="14", name="calculator")]}})

# 翻译后
{"type": "text_delta", "text": "你"}
{"type": "tool_result", "name": "calculator", "ok": True}
```

前端不该知道 `langgraph_node`、`AIMessageChunk`、`ToolMessage` 这些内部结构。翻译层的价值就在这里：**换掉底层框架，前端代码不用改**。

### 生命周期归 RunService，过程归 events

```text
run_start / run_end   ← RunService（有数据库写入、有状态机）
text_delta / tool_call / tool_result ← events（只读 Agent 输出）
```

分开的理由：如果 events 层也发 `run_end`，一次运行可能出现两个结束事件（一个来自流结束、一个来自 service），前端会重复收尾。

### 工具结果只发 `name` + `ok`

```python
{"type": "tool_result", "name": "calculator", "ok": True}
```

不发内容，原因：
- 大结果（读文件）会把 SSE/WebSocket 塞爆。
- UI 的"工具活动"面板只需要"成功了没"，点开详情才按需拉取。

### 失败判定靠前缀约定

```python
def _tool_result_ok(message):
    return not str(message.content or "").startswith("[")
```

工具用 `[ErrorCode]` 前缀表示失败（第 6 章约定），事件层据此判断 `ok`。这是"约定优于解析"：不需要解析每种错误文本，只看前缀。

## 跟着做与验收

1. `--stream --once "你好"`：确认看到 `thread=... run=...`，随后文本输出，最后换行（`run_end completed`）。
2. `--stream --once "计算 99*3"`：确认事件顺序是 `tool_call` → `tool_result` → 文本增量。
3. 对比 `--stream` 与不加 `--stream`：两者最终 answer 一致，区别只是"边跑边出" vs "跑完一次给"。
4. 失败路径：让工具返回 `[InvalidExpression]`，确认事件里 `ok=False`。
5. 观察 run 状态：流式结束后查数据库，`runs.status` 应是 `completed`，`messages` 里 user 和 assistant 各一条。
6. 对照 EvoFlow 的事件模块，列出它多发的字段（usage、step、interrupt 等），写进本章未实现项。
