# 第 10 章 · 第 2 节｜流式消费与 SSE 恢复

## 场景

你看直播看到一半，网络断了。重新连上时，你希望接着刚才看，而不是从头播一遍。直播平台记着"你看到第几分几秒了"，才能续播。

这一节讨论"消费端"：终端怎么吃事件（已实现），以及将来浏览器怎么通过 SSE 吃事件、断线怎么续（未实现）。

## 这一节要实现什么功能

已实现：终端逐条消费事件。目标：把同一事件流经 SSE 推给浏览器，断线后按 `Last-Event-ID` 补齐，不重不漏。

**可验收的行为（已实现部分）**：`--stream --once "你好"` 文本边生成边打印；工具事件单独成行。

**可验收的行为（目标）**：断开连接再带上最后事件 ID 重连，只收到缺失事件。

## 本节业务问题

事件生产出来之后，还有三个问题：

1. **消费方怎么渲染**：终端、浏览器、IDE 各自怎么把事件变成用户看得见的东西。
2. **传输协议**：SSE（`text/event-stream`）怎么编码、怎么断行、怎么处理多行数据。
3. **断线恢复**：网络断了重连，怎么避免"重复播"或"漏播"。

本篇只做到第一层的终端消费；SSE 与恢复是目标形状。

## 调用流程（已实现的终端消费）

```text
service.execute_stream(owner_id, session_id, text)
  ▼
事件逐个到达 _execute_stream_and_print
  ├─ run_start   → print("thread=... run=...")
  ├─ text_delta  → print(text, end="", flush=True)
  ├─ tool_call   → print("\n[工具调用] name args=...")
  ├─ tool_result → print("[工具结果] name ok=...")
  └─ run_end
       ├─ completed → print()（补换行）
       ├─ cancelled → print("运行已取消")
       └─ failed    → print("运行失败 (error_code)")
```

## 已实现的消费代码（`cli/main.py::_execute_stream_and_print`，带注释）

```python
def _execute_stream_and_print(service, owner_id, session_id, text) -> None:
    """事件 → 终端的翻译器：只做渲染，不碰模型和工具。"""

    # service.execute_stream 是生成器：每产出一个事件就进一次循环
    for event in service.execute_stream(owner_id, session_id, text):
        event_type = event.get("type")

        if event_type == "run_start":
            # 生命周期起点：先把 thread / run 报出来，便于事后对照数据库
            print(f"thread={event['thread_id']} run={event['run_id']}")

        elif event_type == "text_delta":
            # 关键：end="" + flush=True，边生成边输出，不攒到最后
            print(event.get("text", ""), end="", flush=True)

        elif event_type == "tool_call":
            # 工具调用单独成行：终端需要换行才看得清参数
            print(f"\n[工具调用] {event.get('name')} args={event.get('args')}")

        elif event_type == "tool_result":
            # ok 由 events/stream.py::_tool_result_ok 判定（看 content 是否以 "[" 开头）
            print(f"[工具结果] {event.get('name')} ok={event.get('ok')}")

        elif event_type == "run_end":
            # 终态收尾：文本增量已打完，这里只补换行或打印失败类别
            if event.get("status") == "completed":
                print()
            elif event.get("status") == "cancelled":
                print("\n运行已取消")
            else:
                print(f"\n运行失败 ({event.get('error_code')})")
```

要迁移到 SSE 时，改的是"这段 print 换成一个 `yield` 编码函数"，事件结构本身不动——这就是第 10.1 节把事件层单独抽出来的原因。

## 关键知识点

### SSE 格式的三条硬规则

```text
event: <类型>\n      ← 可选；前端 addEventListener 用这个名字
id: <序号>\n         ← 可选；断线续播靠它
data: <一行 JSON>\n  ← 必须；多行数据要写成多行 data:
\n                   ← 空行表示"一条事件结束"
```

- 每条事件以**空行**结束。少一个空行，前端会把两条事件粘成一条。
- `data` 里如果有换行，要拆成多行 `data:`，前端会自动用 `\n` 拼回。
- 不能用 `\r\n` 混用（部分客户端解析会出错）。

### 为什么用 SSE 不用 WebSocket

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端 → 客户端） | 双向 |
| 协议 | 普通 HTTP | 升级协议 |
| 断线重连 | 浏览器 `EventSource` 自动重连 | 要自己实现 |
| 代理/防火墙 | 友好 | 可能被拦 |

Agent 流式输出本质是单向"服务端推"，SSE 够用且更简单。

### 断线恢复的关键是 `id`

```text
服务端：每条事件分配单调递增 id
客户端：断线后自动带 Last-Event-ID 重连
服务端：查 id > Last-Event-ID 的事件补发
```

没有 `id` 就只能"重连后从头播"或者"重连后继续但可能漏"。

### 恢复要区分"重播"和"补发"

- **重播**：从头再发一遍——用户会看到重复内容。
- **补发**：只发缺的部分——需要服务端存事件（内存队列或数据库）。

事件存哪是个取舍：内存快但重启丢；数据库慢但可靠。生产环境通常是"内存队列 + 关键事件落库"。

### 终端的渲染取舍

终端不能"局部刷新"，所以 `text_delta` 用 `print(..., end="", flush=True)` 模拟打字机；工具事件用整行输出，因为终端需要换行才看得清。这不是"终端能力弱"，而是"不同消费方渲染策略不同"——这正是事件层要抽象的原因。
