# 第 9 章 · 第 1 节｜内置计算工具与安全求值

> **来源声明（重要）**：`calculator` 是本项目**为教学闭环自造**的工具，EvoFlow 里不存在同名工具——它的算术能力走 `builtins/code_execution_tool.py`（代码执行）与 `builtins/process_tool.py` / `host_direct/terminal_tool.py`（跑一次 Python）。
>
> 所以本节代码**不是仿写对象**，命名与结构不受原版约束；反过来，也不能用它去"对齐"原版。登记见 [EvoFlow 对照台账与差异建议 · 八、本项目自造符号](../../EvoFlow对照台账与差异建议.md)。

## 场景

你给助理一台计算器。助理能按"3+4"算出 7，但你不会给他一台能自己拆开、改线路、连到别处去的机器。计算器就该只算数。

这一节做的事一样：给模型一个 `calculator` 工具，它只能做四则运算。模型即使"想"通过这个工具读文件、执行命令，也只会拿到 `[InvalidExpression]`。

## 这一节要实现什么功能

给 Agent 一个能算数的工具，但绝不允许它执行任意代码：只走 AST 白名单，拒绝调用、属性访问、导入。

**可验收的行为**：`计算 (3+4)*2` → 14；`计算 __import__('os').system('ls')` → `[InvalidExpression] 不支持的表达式成分: Call`。

## 本节业务问题

模型能生成任意字符串，包括：

```
__import__('os').system('rm -rf ~')
open('/etc/passwd').read()
```

如果工具实现是 `eval(expression)`，上面两条都会**真的执行**。这不是"模型会不会乱来"的问题，而是"宿主代码给不给机会"的问题。

需要：一个只能算数、不能调函数、不能访问对象属性的求值器。

## 调用流程

```text
用户输入"计算 (3+4)*2"
  ▼
FakeChatModel 识别 "计算" 前缀，返回 AIMessage(tool_calls=[calculator])
  ▼
LangGraph 工具节点执行 calculator(expression="(3+4)*2")
  ▼
safe_eval("(3+4)*2")
  ├─ ast.parse(mode="eval")
  └─ _eval_node 递归：
       BinOp(Mult) → BinOp(Add) → Constant(3), Constant(4) → Constant(2)
  ▼
返回 "14"
  ▼
ToolMessage("14") 回给模型
  ▼
FakeChatModel 看到 tool 消息 → "工具结果：14"
  ▼
RunService 存入 messages，run → completed
```

## 关键函数与知识点

### AST 白名单是"默认拒绝"

```python
_BIN_OPS = {ast.Add, ast.Sub, ast.Mult, ast.Div, ast.Pow, ast.Mod}
_UNARY_OPS = {ast.UAdd, ast.USub}
```

```python
if isinstance(node, ast.Constant): ...
if isinstance(node, ast.BinOp) and type(node.op) in _BIN_OPS: ...
if isinstance(node, ast.UnaryOp) and type(node.op) in _UNARY_OPS: ...
raise ValueError(f"不支持的表达式成分: {type(node).__name__}")
```

- **不是黑名单**（"禁止 Call"），而是白名单（"只许这几种"）。黑名单永远漏，白名单天然收敛。
- `ast.Call`（函数调用）、`ast.Attribute`（`obj.method`）、`ast.Subscript`（`x[0]`）、`ast.ListComp` 等全部落到最后的 `raise`。

### 两类爆炸防护

```python
if isinstance(node.op, ast.Pow) and abs(right) > _MAX_EXPONENT:
    raise ValueError(f"指数过大（上限 {_MAX_EXPONENT}）")
if isinstance(node.op, (ast.Div, ast.Mod)) and right == 0:
    raise ValueError("除数不能为 0")
```

- `9**9**9` 会让 Python 尝试算一个天文数字，CPU 和内存都撑不住——指数上限直接拒绝。
- 除零不靠 Python 的 `ZeroDivisionError`，而是提前判断，返回模型能理解的文本。

### bool 要单独拦

```python
if isinstance(node.value, bool) or not isinstance(node.value, (int, float)):
    raise ValueError("只支持数字")
```

Python 里 `True` 是 `int` 的子类，`True + True` 会算出 `2`。拦掉 bool，避免"布尔混进算术"这种奇怪结果。

### 错误返回给模型而不是抛异常

```python
except ValueError as exc:
    return f"[InvalidExpression] {exc}"
```

- 抛异常会让整轮 run 变 failed，等于"用户问了个算式，整个对话挂了"。
- 返回错误文本让模型自己修正（"指数太大，换个算法"），这是工具设计里很重要的取舍：**参数错误属于工具级失败，不属运行级失败**。

## 跟着做与验收

1. 正常路径：`计算 (3+4)*2` → `14`；`计算 10/4` → `2.5`。
2. 攻击路径：`计算 __import__('os').system('ls')` → `[InvalidExpression] 不支持的表达式成分: Call`。
3. 爆炸路径：`计算 9**9**9` → `[InvalidExpression] 指数过大（上限 1000）`。
4. 除零：`计算 1/0` → `[InvalidExpression] 除数不能为 0`。
5. 与原版对照（**已核实，不是待办**）：EvoFlow 的 `tools/builtins/` 里没有 AST 白名单实现，`grep -rln "calculator\|ast.parse" evoflow/tools/` 零匹配；它的算术走 `code_execution_tool.py`，安全性靠进程隔离、超时和审批，不靠表达式白名单。
6. 思考题（不做，只记录）：如果严格照原版，这个工具应该被 `code_execution_tool` 取代。代价是什么？——要引入子进程、超时、资源上限、审批，还得决定"允许跑什么代码"。这属于第 10 章的宿主边界问题，不是算术问题。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 算术能力载体 | 无 `calculator`；走 `tools/builtins/code_execution_tool.py`（执行代码）与 `tools/host_direct/terminal_tool.py`（跑一次 Python） | `tools/builtins/calculator.py`，**本项目自造** |
| 安全模型 | 进程隔离 + 超时 + 资源上限 + 审批 | AST 白名单：只放行字面量、四则运算、少量内置函数，**不执行任意代码** |
| 能力边界 | 只要能跑代码，能力几乎无上限 | 只能算表达式；出现变量、循环、导入即拒绝 |
| 依赖 | 子进程 / 容器 | 纯 `ast` + `eval`，无外部依赖 |

**为什么自造**：原版没有可仿写的同构对象。改用 `code_execution_tool` 会让本节变成"进程隔离"专题，与"工具协议"主线错位；AST 白名单能在几十行内把"注册 → schema → 结果协议"讲通。代价是能力窄。
