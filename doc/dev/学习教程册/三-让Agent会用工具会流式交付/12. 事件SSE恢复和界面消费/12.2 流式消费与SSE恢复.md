# 第 12 章 · 第 2 节｜流式消费与 SSE 恢复

## 场景

你看直播看到一半，网络断了。重新连上时，你希望接着刚才看，而不是从头播一遍。直播平台记着"你看到第几分几秒了"，才能续播。

这一节讨论"消费端"：同一条事件流，终端怎么吃、浏览器怎么吃、断线之后怎么补齐。

## 代码走查

| 步骤 | 走哪块代码 | 做什么 | 关键点 |
|---|---|---|---|
| 1 | `events/stream.py` → `ExecuteStream` | 产生事件 | 事件结构必须稳定，两个消费方共用 |
| 2 | `events/sse.py` → `encode_sse_event()` | 一条事件 → 一帧文本 | 见下方三条硬规则 |
| 3 | `events/sse.py` → `decode_sse_payload()` | 帧 → 事件 dict | 只认 `data:` 行，多行拼回 |
| 4 | `events/sse.py` → `heartbeat_comment()` | 心跳注释行 | `: ping`，客户端会忽略但保活 |
| 5 | `events/sse.py` → `EventBuffer` | 最近 200 条事件 | 定长 deque，重启即丢 |
| 6 | `events/sse.py` → `EventBuffer.since()` | 断线补发 | 返回 id > last_event_id 的帧 |
| 7 | `events/sse.py` → `sse_event_stream()` | 编码流 | 先补发，再推新事件 |
| 8 | `app_server/sse.py` → `build_sse_response()` | 包成流式响应 | `text/event-stream` + 禁用缓冲 |
| 9 | `app_server/sse.py` → `create_sse_app()` | 最小 app | `GET /runs/{thread_id}/events`，读 `Last-Event-ID` 头 |
| 10 | `cli/main.py` → `_execute_sse_and_print()` | 终端打印帧 | 与 `--stream` 共用同一事件流 |

## 关键实现

### SSE 的三条硬规则

```python
def encode_sse_event(event: dict, *, event_id: int) -> str:
    """把一条事件编码成 SSE 文本（原版 encode_agui_event 的 SSE 版）。"""
    event_type = str(event.get("type") or "message")
    payload = json.dumps(event, ensure_ascii=False)

    lines = [f"id: {event_id}", f"event: {event_type}"]
    # 规则 2：多行数据要逐行加 data: 前缀，前端会拼回成一条
    for line in payload.splitlines() or [""]:
        lines.append(f"data: {line}")
    # 规则 1 + 3：以空行结束，全部用 \n
    return "\n".join(lines) + "\n\n"
```

对应关系：

| 规则 | 违反的后果 |
|---|---|
| 每条事件以**空行**结束 | 少一个空行，前端把两条粘成一条 |
| 多行数据拆成多个 `data:` | `data:` 里带裸换行，第二条被当成新字段 |
| 行尾统一 `\n` | 混用 `\r\n` 时部分解析器把 `\r` 带进数据 |

### 断线补发靠 id 单调递增

```python
class EventBuffer:
    """最近若干条事件的内存缓冲，用于断线后按 Last-Event-ID 补发。"""

    def __init__(self, maxlen: int = 200) -> None:
        self._items: deque[tuple[int, str]] = deque(maxlen=maxlen)
        self._next_id = 1

    def since(self, last_event_id: int) -> list[str]:
        """返回 id > last_event_id 的事件文本（断线补发）。"""
        return [text for event_id, text in self._items if event_id > last_event_id]
```

客户端重连时 `EventSource` 会自动带上 `Last-Event-ID` 请求头，服务端只要返回"比它大的"，就能做到不重不漏。

### 响应头必须禁用缓冲

```python
_SSE_HEADERS = {
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",  # 关掉 nginx 缓冲，否则事件会被攒着一起发
}
```

少了 `X-Accel-Buffering`，经过 nginx 时会把整段响应攒完再发——"流式"就变成了"一次性"。

## 知识点

### 终端消费和 SSE 消费为什么能共用一套事件

因为它们消费的是**同一个 `ExecuteStream`**。事件结构（`type` + 字段）是契约，渲染方式（print / SSE 帧）只是编码。这也是为什么 `--stream` 和 `--sse` 可以互换而不改生产端。

### 为什么不装 uvicorn 也要写响应层

`app_server/sse.py` 产出的是 `StreamingResponse` 对象，它只要求 Starlette。任何 ASGI 服务器（uvicorn、hypercorn、Granian）都能挂载，也可以用现成的测试客户端直接调。写出来是为了**结构完整、可验证**，不是为了现在就跑一个 HTTP 服务。

### 心跳为什么写成注释行

SSE 规范里以 `:` 开头的行是注释，客户端会忽略。用它保活不污染事件流——如果发一个 `event: heartbeat`，前端还得写一段"忽略心跳"的逻辑。

验收清单：

| 验收 | 预期 |
|---|---|
| 帧格式 | 每帧 `id:` / `event:` / `data:` / 空行 |
| id 单调 | 1 → 5 递增，不跳号 |
| 多行安全 | 事件里含换行时，`data:` 仍是多行且能 `decode_sse_payload` 还原 |
| 补发 | `EventBuffer.since(3)` 返回 id 4、5 两帧 |
| 心跳 | `heartbeat_comment()` 返回 `: ping` 加空行 |
| 响应头 | `build_sse_response` 的 headers 含 `X-Accel-Buffering: no` |
