# 第 10 章 · 第 2 节｜浏览器桥与 Computer Use

> **定位：选学专题，不实现代码、不参与验收。** 原版这部分在 `app/gateway/routers/`（HTTP 桥，带 token 守卫），本项目没有网关层；本节只讲"桥和工具的区别"以及"为什么不该在工具层造浏览器会话"。

## 场景

你让助理帮你在网上订一张票。你能接受他"打开网页、找到座位、点确认"，但你不希望他"随便登你的账号、随便付款、随便改密码"。

浏览器控制比命令执行更危险：**它带着你的登录态，点的是真实按钮**。这一节的重点不是"怎么点"，而是先说清一个事实——**EvoFlow 里这块东西根本不在 harness 的工具层，它在网关里，是给浏览器扩展调的接口**。搞错这一层，代码会写到完全错误的地方。

## 这一节要实现什么功能

**本节不实现代码。** 这一节的目标是把原版的真实形态讲清楚，并说明本项目为什么不做：

| 项 | 结论 |
|---|---|
| 浏览器控制 | 原版是 gateway 的 REST 桥，本项目无网关 → 不实现 |
| Computer Use | 同上，且原版走 PowerShell → 不实现 |
| 工具层封装 | 原版没有 `tools/browser_bridge/`，本项目也不造 |

## 原版的真实形态

EvoFlow 的浏览器与 CUA 能力放在 `backend/app/gateway/routers/` 下，是 FastAPI 路由：

| 文件 | 真实符号 | 作用 |
|---|---|---|
| `browser_bridge.py` | `:46` `class BrowserExecuteRequest` | 请求体模型（动作 + 参数） |
| | `:63` `append_browser_log` | 写浏览器操作日志 |
| | `:89` `execute_command(payload)` | 执行一条浏览器动作（点击、输入、跳转） |
| | `:104` `get_transport` | 查询当前传输方式 / 连接状态 |
| | `:133` `list_tabs` | 列出已打开的标签页 |
| `browser_snapshots.py` | （路由模块） | 页面快照的存取 |
| `cua_bridge.py` | `:49` `class CuaExecuteRequest` | CUA 请求体 |
| | `:77` `_run_ps_action(action, payload)` | 通过 PowerShell 执行桌面动作 |
| | `:111` `execute(payload)` | CUA 路由入口 |
| | `:157` `_to_call_tool_result(method, raw)` | 把底层返回转成统一结果 |

这些路由都带守卫函数 `_bridge_token_guard`、`_org_admin_guard`——这说明它面向的是**外部调用方**（浏览器扩展、桌面端），不是模型直接调的工具。

```text
浏览器扩展 / 桌面端
  ▼  HTTP + bridge token
gateway/routers/browser_bridge.py   ← 校验 token、记日志、转发
  ▼
真实浏览器 / 本机桌面
  ▲
  └── 结果原路返回
```

## 为什么本项目不做这一块

三个硬约束：

1. **本项目没有网关层。** 现在只有 CLI、stdio JSON-RPC 两个入口（`cli/main.py`、`app_server/stdio_rpc.py`），没有一个常驻 HTTP 服务，也没有 token 守卫机制。搬过来就得先造一个网关。
2. **没有外部调用方。** 桥的价值在于"浏览器扩展主动上报"，本项目没有浏览器扩展，桥的另一端是空的。
3. **CUA 依赖 PowerShell。** 原版 `_run_ps_action` 走的是 Windows PowerShell，本项目在 macOS 上跑，即使实现了也是另一套东西。

结论：这一节的价值在于**别把网关层的东西写成工具层的东西**——之前文档里的 `tools/browser_bridge/policy.py`、`tools/cua_bridge.py`、`BrowserSession` 全是照着"工具应该有会话类"的直觉编出来的，原版都没有。

## 如果以后要做，正确姿势

不是"在工具层实现浏览器会话"，而是"工具 → HTTP 调桥"：

```text
模型 tool_call: browser(action="click", target="提交")
  ▼
tools/browser_bridge_tool.py   ← 本项目若做，只需很薄一层
  ▼  httpx.post(gateway + "/browser/execute", token=…)
gateway 的 browser_bridge.execute_command   ← 已有逻辑全在这边
```

工具层只做三件事：拼参数、发请求、把结果转成 `ToolResult`。**所有状态（标签页、连接、快照）都留在网关侧**，工具层不持有会话。

这一段是**设计说明，不是已实现代码**——本仓库没有 `tools/browser_bridge_tool.py`。

## 本节业务问题（即使不做，也要知道）

| 问题 | 后果 |
|---|---|
| 浏览器带登录态 | Agent 能用你的账号做任何事 |
| 点击不可撤销 | 误点"提交订单""删除仓库"直接生效 |
| 页面内容不可信 | 网页里可能藏提示注入（"忽略之前的指令…"） |
| 快照体积大 | 整页截图/HTML 进上下文，直接超预算 |
| 会话被复用 | 两个任务共用同一浏览器，状态互相污染 |

这几条正是原版要在网关侧加 `_bridge_token_guard` 和 `_org_admin_guard` 的原因：**危险的东西放在离模型更远的那一侧**，模型只能发请求，不能直接持有浏览器。

## 与原版的差异

| 项 | EvoFlow | 本项目 |

## 知识点

### "桥"和"工具"的区别

| | 工具（tool） | 桥（bridge） |
|---|---|---|
| 调用方 | 模型 | 外部进程 / 扩展 |
| 位置 | harness 内，和 Agent 同进程 | 网关内，独立服务 |
| 鉴权 | 靠 run 上下文 | 靠 token / 管理员身份 |
| 状态 | 尽量无状态 | 必须持有会话 |

把桥写成工具，会丢掉鉴权；把工具写成桥，会多一层没必要的网络跳转。

### 为什么浏览器能力必须"离模型远一点"

模型能读到网页内容，网页内容是**不可信输入**。如果浏览器会话对象就在工具层、和模型同一个进程，一次提示注入就可能让模型直接操控会话。放在网关后面，模型最多只能发一条格式受限的请求。
