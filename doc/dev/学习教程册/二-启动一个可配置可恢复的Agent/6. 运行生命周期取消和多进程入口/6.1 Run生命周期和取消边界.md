# 第 6 章 · 第 1 节｜Run 生命周期和取消边界

## 场景

你点外卖。下单后商家开始做（状态：已接单），做好了骑手送过来（已完成），商家说卖完了（失败），你中途不想吃了（已取消）。每个订单只能从"已接单"变成一个终态，不能既是"已完成"又是"已取消"。

这一节做的事一样：你每次发消息给 Agent，就是一个"外卖订单"（run）。它从 running 开始，最后必须变成 completed/failed/cancelled 三个之一，且只能变一次。

## 这一节要实现什么功能

给每次对话一个可追踪的状态机：`running` → `completed` / `failed` / `cancelled`，并把失败原因（只存类型名）记在 run 上。

**可验收的行为**：正常一问一答后 `runs` 表多一条 `completed`；模型抛异常时变 `failed` 且 `error_code` 是异常类名；Ctrl+C 后变 `cancelled`。

## 本节业务问题

一次 Agent 执行是一条 Run。Run 要有唯一 id、明确状态转换、可追踪错误类别和资源关闭逻辑。将 run 标成 cancelled 不等于模型请求、工具或后台任务已经停止。

## 调用流程

```text
RunService.execute(owner_id, session_id, text)
  ▼
空文本校验                           # ValueError，未建 run
  ▼
run_id = uuid4().hex                # 每次尝试单独编号；重试不复用
  ▼
runs.start(run_id, session_id, owner_id, now)   # status='running'
  ▼
sessions.add_message(session_id, "user", text)  # 消息写入纳入生命周期
  ▼
agent.invoke(messages, thread_id=session_id)
  ├─ 成功
  │   ├─ sessions.add_message(assistant)
  │   └─ runs.complete(run_id, now)             # → completed
  ├─ Exception
  │   └─ runs.fail(run_id, type(exc).__name__, now)  # → failed，只存异常类型名
  └─ KeyboardInterrupt
      └─ runs.cancel(run_id, now)  +  re-raise   # → cancelled，中断交还入口
```

## 代码走查：每一步走哪里

| 步 | 做什么 | 文件 | 类 / 函数 | 方法 / 调用 |
|---|---|---|---|---|
| 1 | 发起一次 run | `execution/run_service.py` | `RunService.execute` | `run_id = uuid4().hex` |
| 2 | 建 running 记录 | `persistence/run_repository.py` | `RunRepository.start(run_id, session_id, owner_id, now)` | `INSERT INTO runs ... status='running'` |
| 3 | 成功收尾 | `persistence/run_repository.py` | `RunRepository.complete(run_id, now)` | `finish(run_id, "completed", now)` |
| 4 | 失败收尾 | `persistence/run_repository.py` | `RunRepository.fail(run_id, error_code, now)` | `finish(run_id, "failed", now, error_code)` |
| 5 | 中断收尾 | `persistence/run_repository.py` | `RunRepository.cancel(run_id, now)` | `finish(run_id, "cancelled", now)` |
| 6 | 终态写入 | `persistence/run_repository.py` | `RunRepository.finish(run_id, status, now, error_code)` | `UPDATE runs ... WHERE id=? AND status='running'` + `rowcount != 1` 抛 `RuntimeError` |
| 7 | 终态合法值 | `persistence/schema.py` | `runs` 表 | `CHECK (status IN ('running','completed','failed','cancelled'))` |

## 关键函数与知识点

### RunRepository 是什么

`RunRepository` 是 **run 状态机的数据库操作类**，负责管理"一次 Agent 执行"的生命周期状态。

一次用户消息触发一次 Agent 执行 = 一个 run。它把 `runs` 表的所有 SQL 操作封装成方法，保证一次执行只能从 `running` 变成一个终态（completed/failed/cancelled），不会出现两个终态。

```text
start()          → 插入一条 status='running' 的记录
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
     complete()   fail()      cancel()
     (completed)  (failed)    (cancelled)
```

**和 SessionRepository 的区别**：

| | SessionRepository | RunRepository |
|---|---|---|
| 管什么 | 会话和消息历史 | 一次执行的状态 |
| 表 | sessions / messages | runs |
| 关心什么 | 用户聊了什么、谁能看 | 这次执行成功没、失败原因 |

### `RunRepository.finish`（run_repository.py）

```python
cursor = self._conn.execute(
    "UPDATE runs SET status = ?, error_code = ?, updated_at = ? "
    "WHERE id = ? AND status = 'running'",
    (status, error_code, now, run_id),
)
self._conn.commit()
if cursor.rowcount != 1:
    raise RuntimeError(f"run 不存在或已经结束: {run_id}")
```

1. **`WHERE status = 'running'` 是幂等保护**：两个并发结束回调不能把同一 run 都更新成终态；第二个会 `rowcount=0` 抛错。
2. `finish` 只接受 `completed/failed/cancelled` 三种终态，非法值直接 `ValueError`。
3. `complete` / `cancel` / `fail` 是对 `finish` 的薄封装，调用点只表达意图。

### `RunService.execute`（run_service.py）

- **错误类别而非异常原文**：`error_code = type(exc).__name__`，避免把可能含敏感请求内容的 `str(exc)` 原样存库。
- **`KeyboardInterrupt` 单独捕获**：先 `cancel` 形成明确终态，再 `re-raise` 交还入口（CLI 才能正确退出）。
- 返回 `RunResult(run_id, status, answer, error_code)`：入口层只读这个结果，不关心 Agent 内部。

### 取消边界（本节最重要的认知）

```text
标记 cancelled（当前实现）  ≠  真正取消（目标行为）
  ├─ 当前：Ctrl+C → 数据库状态置 cancelled
  └─ 目标：cancellation token 穿透 Agent → 模型请求/工具/子代理/后台进程真正停止
```

当前实现是同步最小版，且**消息和 run 不是同一个事务**：`user` 消息已写入时若 Agent 异常，会留下"有 user 无 assistant"的半轮数据。

## 跟着做

**最小闭环（先做这三步）**

1. 正常一问一答，查 `runs` 表：多一条 `status='completed'`、`error_code=''`。
2. 让模型抛异常（临时把 provider 改成未知值），确认变 `failed` 且 `error_code` 是异常类名。
3. Ctrl+C 中断，确认变 `cancelled` 而不是停在 `running`。

**边界验证（再做这两步）**

4. 对同一条 run 重复写终态，确认第二次抛 `RuntimeError("run 不存在或已经结束")`。
5. 制造"user 已写入、assistant 写入失败"，确认留下半轮数据——这是本节已知缺口。

## 验收

| 项 | 通过标准 |
|---|---|
| 三终态 | completed / failed / cancelled 各能复现一次 |
| 幂等 | 重复终态写入必须失败，不能悄悄覆盖 |
| 错误口径 | 能说清 `error_code` 只存类名、不存 `str(exc)` 的原因 |
| 取消边界 | 能明确说出"标记 cancelled ≠ 真正停止模型/工具" |
| 不作要求 | 不要求实现可传播 cancellation token（那是补齐项） |

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 状态存储 | `live_run_repositories.py` + `session_run_state.py` 两处 | `run_repository.py` 单处 |
| 取消链路 | 有独立取消入口与链路（具体传播范围需按 `runs.py` 核实） | 只把库状态置 `cancelled`，不中断模型 |
| 终态保护 | 需按原版实现核实 | `WHERE status='running'` + `rowcount != 1` 抛错 |
| 事务边界 | 需按原版实现核实 | 消息与 run **不是**同一事务，可能留半轮 |

最后两句的"需核实"是刻意保留的：这两处我还没有逐行读过原版实现，不能写成结论。读到 `runs.py` 后补上。
