# 第 5 章 · 第 2 节｜Checkpoint 与 Thread 恢复

## 场景

你写 Word 文档写到一半，突然断电了。重启后打开 Word，它问你"是否恢复上次未保存的内容？"你点是，接着上次写的位置继续写。

这一节做的事一样：Agent 聊到一半程序退出了，下次同一个 thread_id 再来，LangGraph 自动从 SQLite 把上次的对话状态读回来，接着聊。你不用手动把历史消息再发一遍。

## 这一节要实现什么功能

让 Agent 的内部状态跟着 thread 走：进程退出重开，用同一个 `--thread` 继续聊，模型仍记得前几轮。

**可验收的行为**：第一条命令拿到 thread 与 run 编号；第二条命令带 `--thread` 后回复"第 2 轮"，说明上轮的图状态被读回来了。

## 本节业务问题

业务消息用于查询和展示；checkpoint 保存图状态，供相同 thread 继续执行。二者的写入者、格式和生命周期不同。

## EvoFlow 源码阅读路径

| 环节 | 去哪里读 | 读什么 |
|---|---|---|
| checkpointer provider | `evoflow/agents/checkpointer/provider.py` | 同步 saver 的构造、表初始化、连接管理 |
| 异步 provider | `evoflow/agents/checkpointer/async_provider.py` | 异步版本（本项目没有） |
| 线程状态读取 | `evoflow/agents/checkpointer/thread_state_reader.py` | 单独读取某 thread 的当前状态（本项目没有这个 API） |
| 会话搜索 | `evoflow/agents/checkpointer/session_search.py` | 按 session 检索 checkpoint |
| transcript 裁剪 | `evoflow/agents/checkpointer/omit_transcript.py` | 存 checkpoint 时裁掉大字段 |

原版 checkpointer 目录有 5 个文件；本项目只有一个 `provider.py`（同步、单连接、无裁剪、无状态读取接口）。

## 涉及文件

|---|---|
| `agents/checkpointer/provider.py` | SQLite 长连接 + LangGraph `SqliteSaver` |

## 调用流程

```text
open_checkpointer(db_path)
  ▼
sqlite3.connect(db_path, check_same_thread=False)
  ▼
PRAGMA journal_mode=WAL                    # 与业务库同一文件、读写并发
  ▼
saver = SqliteSaver(conn)
  ▼
saver.setup()                              # 由 LangGraph 建它自己的 checkpoint 表
  ▼
make_lead_agent(model, checkpointer=saver) # agent.py 注入 saver
  ▼
agent.invoke(messages, {"configurable": {"thread_id": session_id}})
  ▼
（进程重启后）沿用同一 thread_id 再次 invoke
  ▼
LangGraph 从 checkpoint 恢复图状态 → 轮数递增
```

## 关键函数与知识点

### `open_checkpointer`（provider.py）

```python
def open_checkpointer(db_path: str) -> tuple[sqlite3.Connection, SqliteSaver]:
    Path(db_path).parent.mkdir(parents=True, exist_ok=True)
    conn = sqlite3.connect(db_path, check_same_thread=False)
    conn.execute("PRAGMA journal_mode=WAL")
    saver = SqliteSaver(conn)
    saver.setup()  # 由 saver 建立它自己管理的 checkpoint 表
    return conn, saver
```

1. **checkpoint 表和业务表共用同一个 SQLite 文件，但 schema 各自独立**：业务表由 `schema.py` 建，checkpoint 表由 `saver.setup()` 建，互不混写。
2. **连接由装配层持有并在进程退出时关闭**：`cli/main.py` 的 `finally` 里统一 `checkpoint_conn.close()`；不要在 Agent 构造函数里偷偷开连接。

### `thread_id` 就是 checkpoint 的恢复键

```python
config = {"configurable": {"thread_id": "local-demo"}}
first = agent.invoke({"messages": [("user", "我叫小林。")]}, config=config)
second = agent.invoke({"messages": [("user", "我叫什么？")]}, config=config)
# second 时 LangGraph 已恢复 first 的图状态
```

- 每次只提交**新**的用户消息；完整历史由 LangGraph 从 checkpoint 读回，业务消息表不负责喂历史。
- `RunService.execute` 用 `session_id` 同时作为 `thread_id`：一条会话 = 一个 thread = 一份 checkpoint。

### fake model 的验证价值

- `FakeChatModel` 按本次传给模型的 **human 消息条数**回复（第 N 轮）——这不是业务轮次，也不是 `runs` 表的记录数（口径见 3.2）。
- 重启进程后沿用原 thread，若返回第 2 轮，说明 checkpoint 恢复的是"整段消息序列"，而不是只把最后一条回显一遍。

## 跟着做

1. 发第一条消息，记下 `thread=` 与 `run=`；**关闭进程**（不是同一个进程连着发）。
2. 用原 `--thread` 再发一条，确认回复变成"第 2 轮"。
3. 用新的 `--thread` 发一条，确认回到"第 1 轮"——验证隔离。
4. 查 `sqlite3` 里的表：确认 checkpoint 相关表由 `saver.setup()` 建，且与业务表同库不同表。
5. 读 EvoFlow `thread_state_reader.py`，记下"单独读取线程状态"这个本项目没有的能力。

## 验收

| 项 | 通过标准 |
|---|---|
| 跨进程恢复 | 必须真的重启进程后仍恢复，同一进程连发不算 |
| 隔离 | 新 thread 回到第 1 轮 |
| 分工 | 能说清业务表与 checkpoint 表各存什么、谁写 |
| 恢复键 | 能说清 `thread_id` 与 `session_id` 当前是一一对应关系 |
| 不作要求 | 不要求异步 saver、状态读取 API、transcript 裁剪 |

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| provider 文件 | `provider.py` + `async_provider.py` | 只有同步 `provider.py` |
| 线程状态读取 | `thread_state_reader.py` 提供独立读取接口 | 无，只能靠 fake 的轮数间接观察 |
| 会话检索 | `session_search.py` | 无 |
| 存储裁剪 | `omit_transcript.py` 存前裁剪大字段 | 无，消息原样落库 |
| 与业务表的关联 | 需按原版文件核对其关联方式 | `session_id` 直接当 `thread_id`，一一对应 |
