# 第 5 章 · 第 1 节｜会话和业务消息存储

## 场景

你去银行办业务，柜员给你开个账户（session）。以后每笔存款取款，都记在存折上（messages）。你随时能翻存折看历史流水，银行也能根据账户号查谁的钱。

这一节做的事一样：建 session 表（账户）和 messages 表（存折流水）。UI 要展示"你有哪些会话、每个会话聊了什么"，就得靠这两张表。Agent 内部怎么想的，不归这两张表管。

## 这一节要实现什么功能

把"用户说了什么、Agent 答了什么"存成可查询的业务数据：建会话、逐条写消息、按 owner 读回历史，跨会话不串线。

**可验收的行为**：建两个 session 各写两条消息，分别读回只看到自己的两条；用错误 `owner_id` 读同一个 session 返回空列表。

## 本节业务问题

UI 要展示会话列表和消息历史，必须有可查询的业务数据；Agent 内部状态由 checkpointer 管理，是另一种用途。两种存储不能混为一个"聊天记录"。

## 关键函数与知识点

### `SCHEMA_SQL`（schema.py）

```sql
CREATE TABLE IF NOT EXISTS sessions (
    id TEXT PRIMARY KEY,          -- 稳定 session/thread 标识
    owner_id TEXT NOT NULL,       -- 所属用户；本地版也保留身份边界
    title TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    role TEXT NOT NULL CHECK (role IN ('user','assistant','tool')),
    content TEXT NOT NULL,
    created_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS runs (
    id TEXT PRIMARY KEY,          -- 一次执行一个 id；重试创建新 id
    session_id TEXT NOT NULL REFERENCES sessions(id),
    owner_id TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('running','completed','failed','cancelled')),
    error_code TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

- **`CHECK` 约束**把 role/status 的合法值写进数据库层，不只是应用层约定。
- **`ON DELETE CASCADE`**：删 session 时消息级联删除；checkpoint 是另一套表，不在这里管。

### `open_database`（db.py）

```text
Path(db_path).parent.mkdir(parents=True, exist_ok=True)   # 首次运行建 data/
conn = sqlite3.connect(db_path, check_same_thread=False)
conn.row_factory = sqlite3.Row        # 查询结果可按列名取
PRAGMA journal_mode=WAL               # 读写并发
PRAGMA foreign_keys=ON                # 让 REFERENCES 真正生效
conn.executescript(SCHEMA_SQL)        # 幂等建表（IF NOT EXISTS）
```

- `executescript` + `IF NOT EXISTS` 保证重复启动不会炸表。
- 连接生命周期由装配层持有并 `close()`，Repository 不自己开连接。

### 同一个 .db 文件里的两套表

CLI 入口用同一个 SQLite 文件同时存业务表和 LangGraph checkpoint 表：

```text
data/workagentharness.db（同一个 SQLite 文件）
├── sessions         ← 业务表，由 persistence/schema.py 建
├── messages         ← 业务表，由 persistence/schema.py 建
├── runs             ← 业务表，由 persistence/schema.py 建
├── checkpoints      ← LangGraph 内部表，由 saver.setup() 建
├── checkpoint_blobs ← LangGraph 内部表，由 saver.setup() 建
└── ...              ← 其他 LangGraph checkpoint 元数据表
```

- **为什么放同一个文件**：学习版简化部署，单机一个文件就行，不用维护两个数据库路径。WAL 模式下读写并发没问题。
- **为什么不用同一个连接**：业务连接和 LangGraph saver 各自管理事务和 schema，分开持有连接便于关闭和测试。实际是两个独立的 `sqlite3.connect()` 连同一个文件，SQLite 自己协调并发访问。
- **职责分工**：业务表给 UI/API 查询会话和消息；checkpoint 表给 LangGraph 恢复图状态。两者写入者不同、格式不同、生命周期不同，不能混为一个"聊天记录"。

### `SessionRepository`（session_repository.py）

| 方法 | 行为 | 关键点 |
|---|---|---|
| `create(session_id, owner_id)` | `INSERT OR IGNORE` | 幂等：同 id 重复创建静默跳过 |
| `add_message(session_id, role, content)` | 插入消息 + 更新 `sessions.updated_at` | 参数化 SQL，禁止拼接输入 |
| `list_messages(session_id, owner_id)` | `JOIN sessions ON owner_id = ?` | **只凭猜到的 session_id 读不到别人的消息** |

- 全部使用**参数化 SQL**（`?` 占位），防止 SQL 注入。
- 当前每个方法单独 `commit()`：方便教学看清每步数据变化；整轮事务（user+assistant+run 原子提交）留到应用服务层补齐。

### 写消息：两个动作必须一起做（`SessionRepository.add_message`）

```python
def add_message(self, session_id: str, role: str, content: str) -> None:
    stamp = _now_utc()                          # 统一 UTC，避免时区混入排序

    # 1. 插入消息本体（参数化 SQL，不拼字符串）
    self._conn.execute(
        "INSERT INTO messages(session_id, role, content, created_at) VALUES (?, ?, ?, ?)",
        (session_id, role, content, stamp),
    )

    # 2. 刷新会话活跃时间：会话列表要按"最近聊过"排序
    self._conn.execute(
        "UPDATE sessions SET updated_at = ? WHERE id = ?",
        (stamp, session_id),
    )
    self._conn.commit()                          # 两条语句一次提交，尽量保证成对落地
```

留意：这里**没有**包事务跨"用户消息 + 助手消息"，所以助手写入失败会留下"有提问无回答"的半轮数据。这是 5.1 已知缺口，第 6 章再讨论怎么补。

### 读历史：用 owner 挡住越权（`SessionRepository.list_messages`）

```python
def list_messages(self, session_id: str, owner_id: str) -> list[sqlite3.Row]:
    return list(self._conn.execute(
        "SELECT m.id, m.role, m.content, m.created_at "
        "FROM messages AS m JOIN sessions AS s ON s.id = m.session_id "
        # 同时校验 session 和 owner：猜到别人的 session_id 也读不出内容
        "WHERE m.session_id = ? AND s.owner_id = ? ORDER BY m.id",
        (session_id, owner_id),
    ))
```

## 验收

| 项 | 通过标准 |
|---|---|
| 隔离 | 两个 session 消息不串线；错误 owner 读不到 |
| 表结构 | 能说出 3 张业务表的字段与 CHECK 约束的作用 |
| 两套表 | 能说清业务表与 checkpoint 表的写入者、格式、生命周期差异 |
| 已知缺口 | 能指出"每方法独立 commit"会导致半轮数据 |
| 不作要求 | 不要求实现分页、迁移、归档 |

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 文件组织 | `persistence/` 20+ 文件，会话服务与消息仓库分开 | 4 文件合并（db / schema / session_repository / run_repository） |
| 会话能力 | `chat_session_service.py` 含归档、删除、搜索 | 只有 `create` / `add_message` / `list_messages` |
| 消息读取 | 仓库层支持分页等读取形态 | 全量 `ORDER BY id` |
| 分享 | `chat_share_repositories.py` + `routers/share.py` | 无（5.3 仅目标设计） |
| 事务边界 | 服务层控制（具体粒度需按文件核实） | 每个方法独立 `commit()`，不做整轮事务 |
