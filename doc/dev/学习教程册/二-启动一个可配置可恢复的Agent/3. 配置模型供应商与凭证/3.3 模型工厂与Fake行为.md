# 第 3 章 · 第 3 节｜模型工厂与 Fake 行为

## 场景

打车：你不关心汽油还是电动，只关心“能不能到机场”。App 负责派一辆能跑的车。

这一节里，配置是“目的地”，工厂 `create_chat_model` 负责派车。Agent 从头到尾只拿到一个 `BaseChatModel`，不知道背后是谁。

## 学习目标

| 层级 | 目标 |
|---|---|
| 主目标 | 能从配置对象得到一个可调用的模型；能说清 `fake` 与 `openai-compatible` 两条分支各在哪一行分叉 |
| 次目标 | 能解释 `FakeChatModel` 三种返回行为的用途，以及“第 N 轮”的准确口径 |

## EvoFlow 源码阅读路径

| 环节 | 去哪里读 | 读什么 |
|---|---|---|
| 工厂入口 | `evoflow/models/factory.py:845` → `create_chat_model(name, thinking_enabled, ...)` | 同名函数，签名完全不同：按模型名查配置、按 `use` 类路径实例化，不做 HTTP |
| 模型解析 | `evoflow/models/resolver.py` → `resolve_run_model()` | 阶梯解析；`require_configured` 控制解析不到时抛错还是返回空串 |
| provider 实现 | `evoflow/models/openai_codex_provider.py`、`claude_provider.py`、`patched_*.py` | 原版多个厂商实现与补丁层 |
| 调用者 | `evoflow/agents/lead_agent/agent.py` | 谁构造模型、谁交给 `create_agent` |

**关键结论**：原版工厂签名是 `(name, ...)`，先进 resolver 找配置行再按类路径实例化；本项目是 `(config, ...)`，直接吃配置对象，内部 `if/elif` 分支。

## 本项目实现路径

```text
cli/main.py: create_chat_model(chat_config)
  ▼ models/factory.py::create_chat_model(config, runtime_model=, runtime_provider=)
      resolve_effective_config(config, ...)          # 合并覆盖，返回新配置
      ├─ provider == "fake"                → FakeChatModel()         # 不联网
      ├─ provider == "openai-compatible"   → ChatOpenAI(...)          # 读密钥
      └─ 其他                              → ValueError("不支持的模型 provider")
  ▼ BaseChatModel（Agent 只认这个接口）
```

| 步 | 做什么 | 文件 | 符号 |
|---|---|---|---|
| 1 | 入口调用工厂 | `cli/main.py` | `create_chat_model(chat_config)` |

## 关键函数与知识点

### `FakeChatModel._generate`：三种行为，不止“回显”

```text
输入 messages
  ├─ 最后一条是 tool   →  "工具结果：<content>"          # 结束工具循环
  ├─ 用户说 "计算 xxx" 且 calculator 已绑定
  │                    →  AIMessage(tool_calls=[calculator])   # 模拟模型决定调工具
  └─ 其他              →  "已收到（第 N 轮）：<最新用户输入>"
```

前两种行为是第三篇能跑通“工具调用 → 结果回传”的前提，不只是教学彩蛋。

**“第 N 轮”的准确含义**：`N = len([m for m in messages if m.type == "human"])`，也就是**这次调用时传给模型的 human 消息条数**。

它不等于：

| 容易混淆的概念 | 是否等于 N |
|---|---|
| 业务轮次（`runs` 表里的记录数） | 否 |
| `messages` 业务表里的消息条数 | 否（那里还含 assistant / tool） |
| 用户实际发了几次话 | 通常接近，但压缩/折叠后可能不一致 |

所以这个数字只能用来观察“模型这侧看到的历史有没有变长”，正好适合验证 checkpoint 是否恢复，不能当作业务口径。

### `resolve_effective_config`（`models/resolver.py`）

- 三个函数：`resolve_provider` / `resolve_model_name` / `resolve_effective_config`。
- 优先级：**运行时参数 > 环境变量 > 配置默认**。
- 返回**新的** `ChatModelConfig`，不改原对象（frozen 的价值在这里体现）。
- 解析结果为空会抛 `ValueError`，不会把空模型名传给供应商。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 工厂签名 | `create_chat_model(name, thinking_enabled, ...)`——按模型名查配置、只实例化 `use` 类路径 | `create_chat_model(config, *, runtime_model, runtime_provider)`——直接吃配置对象，内部 `if/elif` |
| 工厂职责边界 | 只**实例化** provider 类，不发 HTTP | 同一边界（不发 HTTP），但没有 provider 抽象层 |
| 解析阶梯 | 运行时 > agent 配置 > 全局默认（三级） | 运行时 > 环境变量 > 配置（两级，缺 agent 级） |
| provider 覆盖 | 由配置行的 `use` 类路径决定，无环境变量覆盖机制 | `resolve_provider` 支持 `$WORKAGENT_MODEL_PROVIDER` 覆盖 |
| 供应商实现 | 多个：`openai_codex_provider.py`、`claude_provider.py`、`patched_*.py` | 只有 `fake` + `ChatOpenAI`（`openai-compatible`） |
| 超时与重试 | 来自 `ModelConfig.request_timeout` / `max_retries` | 写死 `timeout=30`、`max_retries=0`，刻意让失败可复现 |
