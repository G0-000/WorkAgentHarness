# 第 3 章 · 第 2 节｜模型工厂和凭证边界

## 场景

你打车：不关心是汽油还是电动，只关心"能不能到机场"。App 负责派一辆能跑的车。

这一节里，配置是"目的地"，工厂 `create_chat_model` 负责派车。Agent 从头到尾只拿到一个 `BaseChatModel`，不知道背后是谁。

## 学习目标

| 层级 | 目标 |
|---|---|
| 主目标 | 能从配置对象得到一个可调用的模型；能说清 `fake` 与 `openai-compatible` 两条分支各自在哪里断网、在哪里读密钥 |
| 次目标 | 能说清密钥在哪一层被校验、被脱敏，以及为什么日志里不能出现完整密钥 |

## EvoFlow 源码阅读路径

| 环节 | 去哪里读 | 读什么 |
|---|---|---|
| 工厂入口 | `evoflow/models/factory.py:845` → `create_chat_model(name, thinking_enabled, ...)` | **同名函数**，但签名完全不同：按**模型名**查配置、只实例化 provider 类（`use` 类路径），不做 HTTP |
| 模型解析 | `evoflow/models/resolver.py` → `resolve_run_model()` / `resolve_run_model_with_source()` | 阶梯解析；`require_configured` 控制"解析不到时抛错还是返回空串" |
| 脱敏 | `evoflow/models/credential_sanitize.py` → `sanitize_api_key()` / `is_masked_api_key()` / `resolve_credential_reference()` | 密钥脱敏与引用解析 |
| 凭证自动加载 | `evoflow/models/credential_loader.py` | 从 Claude Code / Codex CLI 的**文件凭证**读 token（OAuth），与本项目同名模块职责不同 |
| provider 实现 | `evoflow/models/openai_codex_provider.py`、`claude_provider.py`、`patched_*.py` | 原版有多个厂商实现与补丁层 |
| 调用者 | `evoflow/agents/lead_agent/agent.py` | 谁构造模型、谁把它交给 `create_agent` |

**关键结论**：原版 `create_chat_model` 与 `credential_loader.py` 都是**同名存在**，但语义差别很大：

- 原版工厂签名是 `(name, ...)`——先进 resolver 找配置行，再按 `use` 类路径实例化；
- 本项目工厂签名是 `(config, ...)`——直接吃一个配置对象，内部 `if/elif` 分支；
- 原版 `credential_loader` 管 CLI 凭证文件，本项目同名模块管 API key 解析与脱敏。

## 本项目实现路径

```text
cli/main.py: create_chat_model(chat_config)
  ▼ models/factory.py::create_chat_model(config, runtime_model=, runtime_provider=)
      resolve_effective_config(config, ...)          # 合并覆盖，返回新配置
      ├─ provider == "fake"                → FakeChatModel()         # 不联网
      ├─ provider == "openai-compatible"   → ChatOpenAI(...)          # 读密钥
      │      └─ 构造异常 → sanitize_error() → ValueError
      └─ 其他                              → ValueError("不支持的模型 provider")
  ▼ BaseChatModel（Agent 只认这个接口）
```

## 走查表：每一步走哪里

| 步 | 做什么 | 文件 | 符号 |
|---|---|---|---|
| 1 | 入口调用工厂 | `cli/main.py` | `create_chat_model(chat_config)` |
| 2 | 合并运行时覆盖 | `models/factory.py` | `resolve_effective_config(config, ...)` |
| 3 | 解析模型名 | `models/resolver.py` | `resolve_model_name(config, *, runtime_override=)` |
| 4 | 解析 provider | `models/resolver.py` | `resolve_provider(config, *, runtime_override=)` |
| 5 | fake 分支 | `models/factory.py` | `FakeChatModel()` |
| 6 | 取密钥 | `models/credential_loader.py` | `resolve_api_key(config)` |
| 7 | 构造真实模型 | `models/factory.py` | `ChatOpenAI(..., timeout=30, max_retries=0)` |
| 8 | 构造失败脱敏 | `models/credential_loader.py` | `sanitize_error(message)` |

## 关键函数与知识点

### `FakeChatModel._generate`：三种行为，不止"回显"

```text
输入 messages
  ├─ 最后一条是 tool   →  "工具结果：<content>"          # 结束工具循环
  ├─ 用户说 "计算 xxx" 且 calculator 已绑定
  │                    →  AIMessage(tool_calls=[calculator])   # 模拟模型决定调工具
  └─ 其他              →  "已收到（第 N 轮）：<最新用户输入>"
```

前两种行为是第三篇能跑通"工具调用 → 结果回传"的前提，不只是教学彩蛋。

**"第 N 轮"的准确含义**：`N = len([m for m in messages if m.type == "human"])`，也就是**这次调用时传给模型的 human 消息条数**。

它不等于：

| 容易混淆的概念 | 是否等于 N |
|---|---|
| 业务轮次（`runs` 表里的记录数） | 否 |
| `messages` 业务表里的消息条数 | 否（那里还含 assistant / tool） |
| 用户实际发了几次话 | 通常接近，但压缩/折叠后可能不一致 |

所以这个数字只能用来观察"**模型这侧看到的历史有没有变长**"，正好适合验证 checkpoint 是否恢复，不能当作业务口径。

### `resolve_effective_config`（`models/resolver.py`）

- 三个函数：`resolve_provider` / `resolve_model_name` / `resolve_effective_config`。
- 优先级：**运行时参数 > 环境变量 > 配置默认**。
- 返回**新的** `ChatModelConfig`，不改原对象（frozen 的价值在这里体现）。
- 解析结果为空会抛 `ValueError`，不会把空模型名传给供应商。

### `credential_loader.py` 三件套

| 函数 | 行为 |
|---|---|
| `resolve_api_key(config)` | 环境变量 `WORKAGENT_MODEL_API_KEY` 优先，其次 `config.api_key` |
| `mask_api_key(key)` | 前 4 位 + `****` + 后 4 位；长度 ≤ 8 全 `*` |
| `sanitize_error(message)` | 正则 `sk-[A-Za-z0-9_-]{8,}` → `[REDACTED]` |

注意一个容易误解的点：当 provider 是 `openai-compatible` 时，**loader 已经保证 `config.api_key` 非空**（否则配置加载阶段就失败）。所以 `resolve_api_key` 里"其次 `config.api_key`"这条兜底，实际作用是在不写 YAML 字面量的前提下，用环境变量**覆盖**配置文件里的占位值。

### 密钥缺失到底在哪一步报错

这是最容易写含糊的地方。真实情况是**三条路径、同一阶段**：

| 配置写法 | 报错位置 | 消息 |
|---|---|---|
| `provider: openai-compatible`，YAML 里没有 `api_key` 或为空 | `config/loader.py`（配置加载） | `openai-compatible provider 需要 api_key` |
| `api_key: ${WORKAGENT_MODEL_API_KEY}`，但环境变量没设 | `config/loader.py` → `_expand_env` | `缺少必需的环境变量: WORKAGENT_MODEL_API_KEY` |
| 以上都通过，但运行期环境变量被清空 | `models/credential_loader.py` → `resolve_api_key` 返回空串，`ChatOpenAI` 构造时报 OpenAI 自己的错 | 供应商错误，已被 `sanitize_error` 脱敏 |

**三条都在模型真正发请求之前**，但只有前两条是"本项目能给出明确契约错误"的。第三条属于外部 SDK 的报错。

## 跟着做

1. 用 `fake` 从 CLI 发一次请求，记录返回文案，确认没有网络请求。
2. 把 provider 改成未知值（如 `anthropic`），确认失败点在工厂而不是模型调用中期。
3. 传 `runtime_model="其他模型"` 观察覆盖；再设 `WORKAGENT_MODEL_NAME` 观察优先级。
4. 读 EvoFlow `models/resolver.py` 的 `resolve_run_model`，把它的三级阶梯与本项目的两级阶梯画在一起，标出本项目缺的那一级（agent 配置）。
5. **（可选）** 真实 provider 实测：需要自己准备 API 额度与密钥。这一步**不是本节通过条件**，没有额度就停在 fake 分支，不影响后续章节。

## 验收

| 项 | 通过标准 |
|---|---|
| 分支 | 能说清 `fake` 与 `openai-compatible` 分别在哪一行、是否需要密钥 |
| 脱敏 | 能说出三件套各自拦的是什么（完整密钥 / 终端展示 / 异常文本） |
| 错误定位 | 能复现"缺 api_key"的两条路径，并说明为什么都在 loader 阶段 |
| Fake 轮数 | 能解释 N 的口径，并说出它**不**等于业务轮次或 run 数 |
| 不作要求 | 不要求有真实 API 额度，不要求跑通真实供应商 |

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 工厂签名 | `create_chat_model(name: str \| None, thinking_enabled, *, thinking_type, invocation_kind, **kwargs)`——按模型名查配置、只实例化 `use` 类路径 | `create_chat_model(config, *, runtime_model, runtime_provider)`——直接吃配置对象，内部 `if/elif` |
| 工厂职责边界 | 文档注释写明：只**实例化** provider 类，不发 HTTP；请求持久化在 provider 内部 | 同一边界（不发 HTTP），但没有 provider 抽象层 |
| 解析入口 | `resolve_run_model(*, agent_code, cfg, require_configured)` 一个函数 | 拆成 `resolve_provider` / `resolve_model_name` 两个函数 |
| 解析阶梯 | 运行时 > agent 配置 > 全局默认（三级） | 运行时 > 环境变量 > 配置（两级，缺 agent 级） |
| 凭证加载 | `models/credential_loader.py`：Claude Code / Codex CLI 的**文件凭证**（OAuth） | 同名模块，职责不同：`resolve_api_key` 解析 API key |
| 脱敏 | `models/credential_sanitize.py`：`sanitize_api_key` / `is_masked_api_key` / `resolve_credential_reference` | `credential_loader.py` 里：`mask_api_key`（展示）+ `sanitize_error`（异常文本） |
| provider 覆盖 | provider 由配置行的 `use` 类路径决定，没有环境变量覆盖 provider 的机制 | `resolve_provider` 支持 `$WORKAGENT_MODEL_PROVIDER` 覆盖 |
| 供应商实现 | 多个：`openai_codex_provider.py`、`claude_provider.py`、`patched_*.py` | 只有 `fake` + `ChatOpenAI`（`openai-compatible`） |
| 超时与重试 | 来自 `ModelConfig.request_timeout` / `max_retries` 字段 | 写死 `timeout=30`、`max_retries=0`，刻意让失败可复现 |

**结论**：`create_chat_model` 是**同名不同签名**；`credential_loader` 是**同名不同职责**。这两处最容易误判成"原版没有"，实际是原版更宽、本项目收窄。
