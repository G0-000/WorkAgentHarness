# 第 3 章 · 第 1 节｜配置契约和配置加载

## 场景

手机连 Wi-Fi，名称和密码不能写死在手机里——得存在"设置"里。换 Wi-Fi 改设置，不用换手机。

这一节做同一件事：把"用哪个模型、连哪个服务器、密钥是什么"从代码里抽到 `config.yaml`。换模型改配置，不碰代码。

## 学习目标

| 层级 | 目标 |
|---|---|
| 主目标 | 能说清一份 YAML 变成 `ChatModelConfig` 对象的每一步，并让每种坏配置在**调用模型之前**报出明确错误 |
| 次目标 | 能说清"配置层"与"凭证层"的分工：配置层只管形状与取值，不负责联网 |

## EvoFlow 源码阅读路径

原版**有**对应的模型配置类，只是名字叫 `ModelConfig`、且用 Pydantic。读的顺序：

| 环节 | 去哪里读 | 读什么 |
|---|---|---|
| 模型配置类 | `evoflow/config/model_config.py:86` → `class ModelConfig(BaseModel)` | **Pydantic** 模型，20+ 字段：`name` / `display_name` / `use`（provider 类路径）/ `model` / `base_url` / `api_key` / `request_timeout` / `max_retries` / `max_tokens` / `context_length` … |
| 模型清单加载 | `evoflow/config/models_yaml.py` | `models.providers` 段的 YAML 读取与校验 |
| 应用级配置 | `evoflow/config/app_config.py:94` → `class AppConfig(BaseModel)` | 一个文件装全局配置（含 agents / organization 等多段），模型只是其中一段 |
| 模型解析 | `evoflow/models/resolver.py` → `resolve_run_model()` | 阶梯：运行时 override > agent 配置 > 全局默认 |
| 调用者 | `evoflow/agents/lead_agent/agent.py` 等 | 谁在真正需要模型名时调 resolver |

**关键结论**：原版是"宽配置（`AppConfig`）+ 多字段模型定义（`ModelConfig`，用 `use` 类路径选 provider）+ resolver 阶梯"。本项目把它收窄成 **一个 chat 段、5 个字段、用字符串 `provider` 分支**，类名也从 `ModelConfig` 改成了 `ChatModelConfig`。

收窄本身是教学取舍（先跑通一条链路），但要清楚代价：原版靠 `use` 字段支持任意 provider 类，本项目只能靠 `if provider == ...` 硬编码；原版 20+ 字段里的超时、重试、上下文长度，本项目一个都没有。

## 本项目实现路径

```text
backend/config.yaml
  ▼ cli/main.py: argparse 取 --config
  ▼ config/loader.py::load_chat_model_config(path)
      yaml.safe_load → raw
      raw["models"]["chat"] → _expand_env 递归展开 ${NAME}
      ChatModelConfig(**chat) → 显式类型关 → 业务校验
  ▼ config/model_config.py::ChatModelConfig（frozen dataclass）
  ▼ models/factory.py::create_chat_model(config)
```

## 走查表：每一步走哪里

| 步 | 做什么 | 文件 | 符号 |
|---|---|---|---|
| 1 | 解析 `--config` | `cli/main.py` | `main()` → `parse_args()` |
| 2 | 进入配置层 | `cli/main.py` | `load_chat_model_config(args.config)` |
| 3 | 读文件、解析 YAML | `config/loader.py` | `Path(...).read_text()` → `yaml.safe_load()` |
| 4 | 取 `models.chat` 段 | `config/loader.py` | `raw.get("models", {}).get("chat", {})` |
| 5 | 展开环境变量 | `config/loader.py` | `_expand_env(value)`，正则 `^\$\{([A-Z0-9_]+)\}$` |
| 6 | 构造配置对象 | `config/model_config.py` | `ChatModelConfig(**chat)`（dataclass，不做类型校验） |
| 7 | **显式类型关** | `config/loader.py` | `isinstance` 检查 provider / model / temperature |
| 8 | 业务校验 | `config/loader.py` | 非空、api_key 必需、temperature ∈ [0,2] |
| 9 | 交给工厂 | `cli/main.py` | `create_chat_model(chat_config)` |

第 6、7 步必须分开看：**dataclass 只保证"有这些字段"，不保证类型**。`temperature: "abc"` 能构造成功，是第 7 步的 `isinstance` 把它拦下来的。这里是本项目一个真实缺陷的修复点——早期版本没有第 7 步，字符串温度会一路走到 `0 <= "abc" <= 2` 抛出裸 `TypeError`。

## 关键函数与知识点

### `ChatModelConfig`（`config/model_config.py`）

```python
@dataclass(frozen=True)
class ChatModelConfig:
    provider: str        # 工厂选择分支的键：fake / openai-compatible
    model: str           # 供应商定义的模型名
    base_url: str = ""   # OpenAI 兼容地址，官方可留空
    api_key: str = ""    # 通常由 ${ENV} 展开得到
    temperature: float = 0.2
```

- `frozen=True`：装配后不可改写，配置来源单一，避免运行中被某次请求悄悄改掉。
- **它不是 Pydantic**。选 dataclass 是因为这里只要一个不可变的值对象，不需要字段级 validator、序列化和嵌套模型；代价是运行时类型校验得自己补（见上表第 7 步）。
- `api_key` 是敏感字段：日志只允许记 provider / model，禁止打印整个对象。

### `load_chat_model_config`（`config/loader.py`）

校验顺序是固定的，**错误的先后顺序本身就是契约**：

```text
文件存在 → 顶层是对象 → models.chat 是对象 → 构造 dataclass
        → 类型关 → 非空关 → api_key 关 → temperature 关
```

真实错误对照（已实测，全部在调用模型之前）：

| 坏配置 | 异常类型 | 消息 |
|---|---|---|
| 文件不存在 | `FileNotFoundError` | `找不到配置文件: <path>` |
| 顶层是 list | `ValueError` | `配置文件顶层必须是对象` |
| `models.chat` 是 list | `ValueError` | `models.chat 必须是对象` |
| 多余字段 / 缺 `provider` | `ValueError`（包装 `TypeError`） | `models.chat 配置字段无效: ...` |
| `provider: 123` | `ValueError` | `models.chat.provider 必须是字符串` |
| `provider: ''` | `ValueError` | `models.chat.provider 不能为空` |
| `temperature: "abc"` | `ValueError` | `models.chat.temperature 必须是数字` |
| `temperature: true` | `ValueError` | `models.chat.temperature 必须是数字` |
| `temperature: 3` | `ValueError` | `models.chat.temperature 必须在 0 到 2 之间` |
| `openai-compatible` 无 api_key | `ValueError` | `openai-compatible provider 需要 api_key` |
| `${WORKAGENT_MODEL_API_KEY}` 未设 | `ValueError` | `缺少必需的环境变量: WORKAGENT_MODEL_API_KEY` |

除"文件不存在"外，配置层统一抛 `ValueError`，调用方只需要接一种异常。

### `_expand_env` 的边界

`_ENV_PATTERN = r"^\$\{([A-Z0-9_]+)\}$"` 只匹配**独占整个字段**的 `${NAME}`。`abc${X}` 这类拼接文本不会展开——避免把普通文本里的 `${}` 误当变量。

变量名为空或不存在时，报错只带变量名、不带值：

```python
raise ValueError(f"缺少必需的环境变量: {name}")
```

## 跟着做

1. 不改代码，口头走一遍：文件 → `raw` → `chat` → `_expand_env` → `ChatModelConfig` → 返回。
2. 依次制造 4 种坏配置：`temperature: 3`、`temperature: "abc"`、`provider: ''`、删掉 `model` 字段。记录每次的异常类型与消息，和上表对照。
3. 把 `api_key` 写成 `${WORKAGENT_MODEL_API_KEY}` 但不设环境变量，确认报错只出现变量名。
4. 修复配置后从 CLI 跑一次，确认读取的是哪个配置文件路径。

## 验收

| 项 | 通过标准 |
|---|---|
| 配置形状 | 能写出 `ChatModelConfig` 的 5 个字段与各自默认值 |
| 校验顺序 | 能说清为什么"类型关"必须在"业务校验"之前（否则裸 `TypeError` 泄漏） |
| 错误契约 | 上表 11 行至少能自主复现 5 行，且异常类型与消息一致 |
| 不作要求 | 不要求背 LICENSE 式的条款；不要求实现 Pydantic 迁移 |

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 模型配置类 | `config/model_config.py::ModelConfig`，**Pydantic `BaseModel`** | `config/model_config.py::ChatModelConfig`，**frozen dataclass** |
| 字段数量 | 20+：`name` / `display_name` / `description` / `use` / `model` / `base_url` / `api_key` / `request_timeout` / `max_retries` / `max_tokens` / `context_length` … | 5 个：`provider` / `model` / `base_url` / `api_key` / `temperature` |
| provider 选择 | `use` 字段存 **provider 类路径**（如 `langchain_openai.ChatOpenAI`），可接任意实现 | 字符串 `provider` + 工厂里 `if/elif` 硬编码分支 |
| 名字层级 | `name`（唯一标识）与 `model`（真实模型名）**两个名字** | 只有一个 `model` |
| 运行参数 | 超时、重试、max_tokens、上下文长度都在配置里 | 工厂里写死 `timeout=30`、`max_retries=0`，配置管不到 |
| 配置范围 | `models_yaml.py` 管 `models.providers` 段 + `app_config.py` 管全局 | 只有 `models.chat` 一段 |
| 模型解析 | `models/resolver.py::resolve_run_model()`，三级阶梯（运行时 > agent > 全局） | 拆成 `resolve_provider` / `resolve_model_name` 两个函数，两级阶梯（运行时 > 环境变量 > 配置） |
| 命名沿革 | EvoFlow：`ModelConfig`（Pydantic，20+ 字段） | AgentFlow 第一遍：`ChatModelConfig`（`@dataclass`，同样 5 字段，`temperature` 默认 0.3）→ 本项目：沿用 `ChatModelConfig`，改成 `frozen=True`、`temperature` 默认 0.2、字段必填 + 显式类型校验 |

**结论**：不是"原版没有、本项目自造"，而是"**同名概念、不同类名、人为收窄**"。属于改名的有 `ModelConfig → ChatModelConfig`；属于拆分的只有 resolver 一个函数变两个；真正的简化是字段数量、`use` 类路径机制、以及运行参数写死。
