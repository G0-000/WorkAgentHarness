# 第 4 章 · 第 2 节｜单轮执行与结果返回

## 场景

餐厅点菜：你说"来一份鱼香肉丝"，服务员记下递给厨房，做好端出来。你不用管厨房怎么炒。

这一节：给 Agent 一句话，它跑完整个图，你从结果里掏出最后一条消息。图内部走了几个节点，不关你的事。

## 学习目标

| 层级 | 目标 |
|---|---|
| 主目标 | 说清 `agent.invoke` 的输入形状与输出形状，知道"最后一条消息"为什么是回复 |
| 次目标 | 说清"同一 thread 第 2 轮"能成立，是因为背后有 checkpointer，而不是因为 CLI 记住了什么 |

## EvoFlow 源码阅读路径

原版没有"单轮函数"这种东西——一次对话被完整地包在 run 生命周期里。读的顺序：

| 环节 | 去哪里读 | 读什么 |
|---|---|---|
| 入口路由 | `backend/app/gateway/routers/runs.py`、`chat_sessions.py` | 请求 schema、权限依赖、响应/事件返回方式 |
| 会话与消息 | 同目录 `chat_sessions.py` | 一条消息如何被落成 session + message |
| 运行控制 | `runs.py` | run 的创建、状态推进、取消入口 |
| Agent 调用 | `evoflow/agents/lead_agent/agent.py` | 图在什么位置被 invoke / stream |

**关键结论**：原版"取回复"这一步藏在 run 生命周期内部，没有独立的薄函数可对照。本项目把它抽出来讲，是为了先看清 `invoke` 契约，不代表原版有同名设计。

## 本项目实现路径

真实路径只有一条（CLI → `RunService`），但可以分成两层看：

```text
CLI: --once "你好"
  ▼ cli/main.py::_execute_and_print(service, owner_id, session_id, text)
  ▼ execution/run_service.py::RunService.execute(owner_id, session_id, text)   ← 第 5 章正式实现
      ├─ 空文本校验
      ├─ 建 run 记录（status=running）
      ├─ 写 user message
      ├─ agent.invoke({"messages": [...]}, {"configurable": {"thread_id": session_id}})
      ├─ 取 result["messages"][-1].content
      ├─ 写 assistant message
      └─ 收尾 run（status=completed）
  ▼ RunResult(run_id, status, answer, error_code)
```

**本节只看中间那三步**（invoke → 取末条 → 返回）；建 run、写库、收尾属于第 5 章，这里先当作黑盒。

## 走查表：每一步走哪里

| 步 | 做什么 | 文件 | 符号 |
|---|---|---|---|
| 1 | 入口发起一轮 | `cli/main.py` | `_execute_and_print` → `service.execute(...)` |
| 2 | 空文本校验 | `execution/run_service.py` | `RunService.execute` 开头 `if not text.strip()` |
| 3 | 调 Agent | 同文件 | `self._agent.invoke({"messages": [...]}, {"configurable": {"thread_id": session_id}})` |
| 4 | 取回复 | 同文件 | `str(result["messages"][-1].content)` |
| 5 | 返回结构 | 同文件 | `RunResult(...)` → CLI 打印 |

第 3、4 步是本节的实质；第 1、2、5 步只是外壳。

## 关键函数与知识点

### `agent.invoke` 契约

```python
result = agent.invoke(
    {"messages": [("user", text)]},                                  # 输入形状
    {"configurable": {"thread_id": session_id}},                     # 有 saver 才需要
)
answer = str(result["messages"][-1].content)                         # 输出形状
```

| 项 | 说明 |
|---|---|
| 输入 | `{"messages": [...]}`——消息列表是 LangGraph Agent 的标准输入形状，`("user", text)` 是简写元组 |
| 输出 | `result["messages"]` 是执行后的**全部**消息（user 原样 + assistant 回复，可能有 tool 消息），**最后一条**才是本次回复 |
| `thread_id` | 只有装了 checkpointer 才有意义；它决定"这批状态存到哪个线程" |
| 无 saver 时 | 传 `configurable` 也不会持久化，图状态随调用结束丢弃 |

### "第 2 轮"到底靠什么成立

这是最容易搞混的一点。`FakeChatModel` 的轮数来自 `len(human 消息)`，而 human 消息能累积，**必须**有 checkpointer 把上一轮的状态存下来。

| 场景 | 第 2 次调用的回显 | 原因 |
|---|---|---|
| 直接 `agent.invoke`（`make_lead_agent` 传 `checkpointer=None`） | 第 1 轮 | 每次都是新历史 |
| 走 CLI（`cli/main.py` 已传 `saver`） | 第 2 轮 | checkpointer 把上一轮 messages 存进 SQLite，按 `thread_id` 回填 |

所以 4.2 的"轮数递增"实验**依赖第 5 章的 checkpointer**。这是有意的前置使用：CLI 必须有 saver 才能支持 `--thread`，第 5 章只是回头解释它。写笔记时要把这条依赖标出来，别误以为是 CLI 自己记着历史。

### 为什么不建议在 4.2 造一个 `answer_once`

早期版本这里写过一个只有 6 行的 `answer_once(agent, text)` 薄函数，作为"文本进、文本出"的最小边界。它从未进入代码——真实入口一直走 `RunService.execute`。

保留一个代码里不存在的函数会让读者以为项目里有这个 API。本节的替代做法是：把 `RunService.execute` 拆成"外壳 + 三步内核"，只讲内核。要看纯边界，直接读 `execute` 的那三行。

## 跟着做

1. 用 `make_lead_agent(model)`（不传 checkpointer），连续 invoke 两次同样的输入，观察两次都是"第 1 轮"。
2. 再走 CLI（`--once` 两次，第二次带 `--thread`），观察变成"第 2 轮"。
3. 打印 `result["messages"]` 的完整列表，确认最后一条的 `type` 是 `ai`（assistant），前面还有 system 与 human。
4. 传空字符串，确认在调用模型前就被拒（不会产生 run 记录）。
5. 对照 EvoFlow `routers/runs.py`、`chat_sessions.py`，记录原版请求/响应 schema 比本项目多哪些字段。

## 验收

| 项 | 通过标准 |
|---|---|
| 契约 | 能写出输入与输出的准确形状，并说出"最后一条"为什么是回复 |
| 两种模式 | 能自己复现"无 saver → 永远第 1 轮"和"有 saver → 递增" |
| 依赖说明 | 能说清轮数递增靠 checkpointer，不是靠 CLI |
| 边界 | 能指出空文本在模型调用之前被拒 |
| 不作要求 | 不要求实现流式（第 12 章） |

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 入口形态 | HTTP 路由 `routers/runs.py` + `chat_sessions.py`，带请求 schema 与权限依赖 | CLI `--once` + `_execute_and_print` |
| 单轮函数 | 无独立薄函数，包在 run 生命周期里 | 同样没有（早期文档里的 `answer_once` 未落地） |
| 输出形态 | 响应对象 / 事件流 | `RunResult` 数据类 |
| 取回复方式 | 在 run 内部随流式或最终结果处理 | `result["messages"][-1].content` |
