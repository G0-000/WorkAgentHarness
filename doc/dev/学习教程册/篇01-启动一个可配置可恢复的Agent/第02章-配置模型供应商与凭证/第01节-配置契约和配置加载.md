# 第 2 章 · 第 1 节｜配置契约和配置加载

## 本节业务问题

模型选择不是散落在 CLI 里的字符串分支。先把 YAML 和环境变量转成有类型、有校验的配置对象，再交给模型工厂。这样错误会在调用模型前出现，也不会把密钥写入代码。

## 调用流程

```text
backend/config.yaml
    → load_chat_model_config(path)
    → 展开 ${WORKAGENT_MODEL_API_KEY}
    → ChatModelConfig 字段校验
    → 返回不可变配置对象
```

## 代码解释

- [model_config.py](../../../../../backend/packages/harness/workagentharness/config/model_config.py)：`ChatModelConfig` 是模型构造契约，包含 provider、model、base_url、api_key、temperature；冻结 dataclass 防止装配后被请求随意修改。
- [loader.py](../../../../../backend/packages/harness/workagentharness/config/loader.py)：`yaml.safe_load` 读取配置；`_expand_env` 递归展开独占字段的 `${NAME}`；`load_chat_model_config` 再检查 provider、model、密钥和温度范围。
- [config.yaml](../../../../../backend/config.yaml)：默认是 `fake`，所以学习开始时不依赖网络或密钥。

## 跟着做

1. 先不改代码，手动指出配置从文件到 `ChatModelConfig` 的每一步。
2. 把 provider 改为空值、temperature 改成 3，观察错误是否在模型创建前出现。
3. 切换为 `openai-compatible`，先不设置环境变量，确认错误提示只指出变量名，不输出秘密值。
4. 修复配置后从 CLI 入口运行一次，并记下实际读取的配置文件路径。

## 本节验收

给出一份配置字段表；成功配置产生类型化对象；缺文件、缺字段、缺环境变量、越界温度分别产生可解释错误。不能以“YAML 能解析”作为本节通过条件。
