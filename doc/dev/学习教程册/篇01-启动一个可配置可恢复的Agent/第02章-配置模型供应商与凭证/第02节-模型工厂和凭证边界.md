# 第 2 章 · 第 2 节｜模型工厂和凭证边界

## 本节业务问题

Agent 只需要统一的 chat model 接口，不应知道请求最终发给哪家供应商。工厂负责从配置选择模型实现；凭证由配置层注入，调用日志不能打印密钥。

## 调用流程

```text
ChatModelConfig.provider
    ├─ fake → FakeChatModel（离线、确定性）
    └─ openai-compatible → ChatOpenAI（超时、重试参数）
                       ↓
                 BaseChatModel.invoke
```

## 代码解释

- [factory.py](../../../../../backend/packages/harness/workagentharness/models/factory.py)：`FakeChatModel._generate` 按输入用户消息数和最后一条内容生成可复现答案；恢复同一 thread 时轮数会增长，便于观察状态恢复。
- `create_chat_model` 将 provider 分支集中在工厂；Agent 依赖 `BaseChatModel`，不需要 import `ChatOpenAI`。
- OpenAI-compatible 分支设定有限 timeout，当前关闭自动重试，让失败容易观察；真实限流策略、供应商差异和凭证优先级尚未覆盖。

## 跟着做

1. 先以 `fake` 从 CLI 发起请求，记录答案格式和模型没有联网的证据。
2. 把未知 provider 传给工厂，确认失败位置和错误类别。
3. 读 EvoFlow `models/resolver.py`、`models/credential_loader.py`、`models/factory.py`，逐项记录 WorkAgentHarness 还缺哪些模型解析与供应商行为。
4. 真实 provider 只能在本机设置环境变量后验证；不要把密钥放进 YAML、终端记录或学习笔记。

## 本节验收

能解释配置对象如何选择模型类、Agent 为何不依赖具体供应商，以及真实 provider 未验证时仍然存在的功能差异。
