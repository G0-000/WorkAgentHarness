> 所属篇：启动一个可配置、可恢复的 Agent

## 本章要做出的东西
建立可启动、可取消、可关闭的执行生命周期，让 HTTP、CLI、本地 App Server 复用同一核心用例。入口可以不同，状态与取消语义不能分叉。

## EvoFlow 阅读顺序
1. 读 `session_execution/`，定位执行创建、状态变更、资源清理、后台任务所有权。
2. 读 `cancellation/`，跟 token/event 从入口传播到 Agent、工具、子代理；分别标记可取消与不可取消调用。
3. 从 Gateway route 追请求 id/run id/session id、重复提交和客户端断连行为。
4. 读 `cli/main.py`、`cli/commands/` 的参数/错误映射；读 `app_server/stdio_rpc.py`、`chat_bridge.py`、`embed.py` 的协议、核心调用与退出清理。
5. 核对平台 event loop、子进程、路径、信号和关闭顺序；支持平台必须以当前源码证据为准。

## WorkAgentHarness 仿写顺序
1. 写共享核心 `RunUseCase`：验证后输入→创建 run→调用 Agent→写唯一终态。HTTP/CLI 仅做输入输出适配。
2. 定义 run 状态机与 cancellation token，从入口透传到 Agent/工具；明确每个耗时边界怎样响应取消。
3. 先实现 CLI 调同一个核心用例，再实现 HTTP adapter；不在各入口重复业务逻辑。
4. 为 App Server 写协议 schema、request id、错误、超时和退出清理，同样调用核心 use case。
5. 若任务需脱离请求协程运行，定义 owner、并发上限、进程退出等待/终止和孤儿恢复策略。
6. 所有成功/异常/取消/关闭路径都执行幂等资源清理，只写一次终态。

## 分层练习与出口
L1 启动/完成/取消一个 fake run；L2 CLI 与 App Server 各跑一次；L3 完整 run 状态、stdio RPC、桥接与平台适配；L4 验证断连、重复启动、取消传播、退出清理。注入正常完成、取消、断连、重复请求、SIGTERM、RPC 超时，检查终态、取消到达和资源释放；交付生命周期图与跨入口一致性记录。
