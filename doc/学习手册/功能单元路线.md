# 功能单元路线：从最小闭环到 EvoFlow 快照对齐

> 对照快照：EvoFlow `62a4117ceff4626213ad434eae6b311bcc3bcfe1`；AgentFlow 第一遍基线：`d39429698752ce01770896c2be887d2ca952cb2b`。开始每个单元前先确认本机 checkout/commit，并复核路径。这里的“完整”指对该快照中适用用户行为和可观察边界建立实现或有证据的排除，不要求相同内部实现。

本路线按功能行为拆单元，不采用 M0–M8 作课程骨架。可以跳转，但同一单元必须从最小闭环走到完整验收；相邻单元之间没有固定的全局阶段。稳定功能 ID 见[唯一活功能清单](功能清单.md)。本文件给出源码范围、每项的最小实现和完整对齐出口；功能清单记录实际学习/实现状态和证据。

## 怎么走每个单元

1. **从场景出发**：写出用户、入口、输入、可见结果、权限主体和涉及状态。
2. **追 EvoFlow 真实链路**：入口/注册 → 调用者 → 核心行为 → 持久化/外部依赖 → 返回/事件；补源码符号、测试和用户文档证据。组件存在但找不到接线时标记“待追入口”。
3. **做最小闭环**：先用假模型、内存库或本地 fixture 做一条成功路径；能从操作看到确定结果。
4. **逐层补完整**：接上真实接口和持久化；覆盖配置、变体、失败、权限、并发/取消、重启恢复、观测与产品入口中适用的部分。
5. **对照第一遍**：只记录 AgentFlow 实际做到了什么、哪里误判/漏接、哪些文档已过时；不以旧章节名推断能力完成。
6. **验收和讲解**：端到端操作可复现；列出已实现、差异、排除和未验证边界；能讲清输入到结果及状态生命周期。

**最低验收证据**：功能 ID、三仓库 commit、精确路径/符号、入口和调用链、配置及外部依赖、运行命令/操作、预期与实测、失败/边界结果、日期。单测通过不等于真实入口已集成；mock 通过须注明真实依赖尚未验证。

## AgentFlow 第一遍复盘方式

AgentFlow 的 M0–M8 和记载它的 `doc-dev/`、`doc-code/` 是历史证据，不直接继承其章节结构或“完成”结论。对每个 WAH ID 回到第一遍基线检查：

- 实际入口是否存在，是否到达声称的组件；区分调用链、孤立模块、stub 和 mock。
- 数据结构、配置、迁移、重启恢复和权限是否一致；“有 JWT/有 bus/有 runner”不等于覆盖了路由/渠道/生产执行路径。
- 测试是 unit、integration 还是端到端；记录真实依赖是否参与、失败路径是否断言。
- 文档代码片段/路径/命令是否匹配当时 commit；旧路径只作历史线索，不复制进新实现。
- 重学采用“场景→EvoFlow 源码→最小实验→补齐→对照→验收”，避免先照抄第一遍目录或固化章节再找功能。

## 版本变化和功能范围控制

EvoFlow 是活动项目，快照变化时不要把旧路径当现状。为本次学习冻结 commit；新版本新增/删除行为时先做差异盘点，明确本轮是否纳入。每个 ID 可拆分为多个独立权限/生命周期/验收行为；拆分后保留旧 ID 并注明迁移。实现方式允许不同，用户可见行为、数据/权限语义、生命周期和接口契约需要对齐。依赖许可或外部服务不可复制时，写明范围、替代方案和剩余行为差异，并标为“有依据排除”或“未验证”，不能标“已验收”。
